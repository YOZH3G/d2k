# Как выпустить релиз D2K

Этот документ — чтобы релиз мог выпустить не только автор. Здесь описано то,
что уже действует. Читать целиком стоит один раз, дальше хватит раздела
«Порядок».

---

## Единственная точка входа

GitHub → **Actions** → **Signed D2K release** → **Run workflow**, ветка `main`.
Из терминала то же самое:

```sh
gh workflow run "Signed D2K release" --repo necronicle/d2k --ref main -f dry_run=false
```

Других путей нет. Локальная сборка (`scripts/build-router.sh`,
`scripts/package-update.py`) нужна для проверки, но выпуск, который увидят
роутеры, делает только этот workflow.

---

## Порядок

1. **Работать и коммитить в `main`.** Каждый push запускает `ci.yml`; в нём
   есть задание с полной сборкой выпуска на девять арок, проверками под QEMU,
   упаковкой и подписью **тестовым** ключом. Ничего не публикуется.
2. **Дождаться зелёного CI** на коммите, который выпускаете.
3. **Пробный прогон:** тот же workflow с `dry_run` (галочка стоит по
   умолчанию). Он проходит весь путь, включая проверку загрузочных комплектов
   и машину состояний публикации, но без сетевых изменений. Ручные запуски
   и ежедневное переподписание стоят в одной очереди
   (`d2k-stable-publisher`): второй запуск ждёт первый, а ждущий
   заменяется следующим. Запускайте выпуск по одному.
4. **Выпуск:** снова Run workflow, галочку `dry_run` **снять**. Поле
   `release_id` можно оставить пустым — номер будет `d2k-<12 знаков коммита>-<время коммита>`.

Всё. Дальше роутеры сделают сами.

### Что происходит при выпуске

Задание `build` собирает девять арок из чистой копии коммита, гоняет тесты
под QEMU и пакует для каждой арки рабочий архив `d2k-runtime-<арка>.tar` и
отдельный загрузочный комплект `d2k-bootstrap-<арка>.tar`. Задание `publish`
работает только для `main` и только в окружении `d2k-signing`:

1. подписывает `manifest.json` и описатели загрузочных комплектов;
2. создаёт релиз-черновик с тегом, равным номеру выпуска, загружает все
   файлы, проверяет каждый по хешу и только потом снимает черновик;
3. переставляет **канал** — релиз с тегом `d2k-channel-stable`: кладёт
   неизменяемую запись `checkpoint-<номер>-<хеш>.bin`, затем заменяет
   `stable.json` и `stable.json.sig` и перечитывает их с проверкой подписи.

Канал переставляется последним: незагруженный или битый выпуск роутеры не
увидят. Публикация — это движение указателя `stable.json`, а не появление
файлов.

### Что делают роутеры

- Раз в сутки в окне **03:00–05:00 по часам роутера** (минута своя у каждой
  установки) обновлятор проверяет канал, скачивает архив своей арки,
  сверяет подпись и хеш и устанавливает: остановка служб, снимок личного
  состояния, переключение, запуск.
- Новый выпуск **120 секунд** проверяется: release ID процессов, связь
  контроллера с датапатом, свежий пульс, ответ панели, свои правила. Сбой —
  откат на прежний выпуск и **карантин** этого выпуска: ночью он больше не
  ставится, вручную — только явно.
- В панели есть «Проверить» и «Установить» — то же самое без ожидания ночи.
- Новая установка командой из README ставит выпуск из канала сразу и
  включает автообновление.

## Правила, нарушение которых видно не сразу

**Номер выпуска не переиздаётся.** Повторная публикация того же
`release_id` отвергается. Нашли дефект в опубликованном выпуске — выпускайте
следующий.

**Сломанный выпуск не «откатывается» на сервере.** Роутер сам откатится и
поставит его в карантин, но на роутерах, где выпуск прошёл проверку, он
останется. Лечится следующим выпуском, а не правкой канала руками.

**Формат личного состояния должен читаться в обе стороны.** Каталог,
`config`, ключ Telegram и прочее должны быть понятны и новому, и прежнему
выпуску: откат возвращает прежний код к текущему состоянию. Несовместимая
миграция в v1 не поддерживается — это отдельный проект.

**Стабильная часть выпуском не обновляется.** `d2k-update-boot`,
`d2k-service-adapter`, `S98d2k-update` и `uninstall.sh` лежат в
`/opt/d2k/boot` вне выпусков и ставятся только загрузочным комплектом при
установке. Изменения в них дойдут до уже установленных роутеров только
через переустановку.

**Канал протухает за 7 суток.** Подпись `stable.json` действует неделю;
ежедневный запуск того же workflow в 03:17 UTC переподписывает его, даже
если нового выпуска нет. Если Actions не работал неделю, роутеры перестанут
ставить обновления (не сломаются — просто не будут видеть свежего канала).
Лечится ручным запуском workflow.

**Протокол датапата и контроллера.** Выпуск, который меняет wire-протокол
`d2kd`↔`d2kc`, ставится только вместе — это и так одна пачка. Но
обновлятор откажет выпуску, если не совпадают версии, которые проверяет
манифест (`update/FORMAT.md`): ABI, протокол, формат состояния, версия
обновлятора.

**`builds/` в репозитории — только для первой установки.** Установщик из
README сначала ставит бинарники из `builds/` ветки `main`, а затем переводит
роутер на подписанный выпуск. Рабочий код роутеры получают из выпуска,
поэтому `builds/` не обязательно обновлять к каждому релизу.

## Ключ подписи

Ed25519. Закрытая часть:

- на машине владельца — `~/.ssh/d2k_release_signing_ed25519.pem` (права
  0600), открытая — рядом, `…pub.hex`;
- на GitHub — секрет `D2K_ED25519_PRIVATE_KEY` окружения `d2k-signing`.

Открытая часть закреплена в трёх местах, и они должны совпадать:
переменная репозитория `D2K_SIGNING_PUBLIC_KEY`, строка `key=` в переменной
`D2K_UPDATE_PUBLIC_CONFIG_TEMPLATE` (она попадает в `update.conf`
загрузочного комплекта) и `UPDATE_KEY` в `scripts/install.sh`. Ещё нужна
переменная `D2K_SIGNING_ENVIRONMENT_READY=true`.

В репозиторий закрытый ключ не кладётся никогда.

**Отличие от z2k.** В z2k ключ живёт только у владельца, а робот лишь
проверяет подпись: захват репозитория не даёт подделать релиз. Здесь ключ
лежит в секрете Actions — это проще, но захват репозитория с доступом к
окружению `d2k-signing` даёт и подпись. Если нужна модель z2k, окружению
`d2k-signing` надо добавить обязательное подтверждение владельцем
(Settings → Environments → Required reviewers) или перенести подпись на
машину владельца.

**Потеря ключа** — роутеры на автообновлении больше не примут ни одного
выпуска; останется только переустановка. Храните копию.

**Смена ключа** предусмотрена форматом (переходный ключ подписывается
старым, см. `update/FORMAT.md`), но ни разу не проверялась. Без отдельной
проверки в лаборатории не делать.

## Проверка перед и после

Перед выпуском, если менялось что-то в обновлятор, службах или скриптах
`files/`:

```sh
make -C update check san
sh scripts/lab-update.sh   # Docker, ~15 минут: A→B, откат сломанного B,
                           # обрыв питания, кончившееся место
```

После выпуска:

```sh
curl -fsSL https://github.com/necronicle/d2k/releases/download/d2k-channel-stable/stable.json
```

должен показать новый `release_id`. На роутере — панель, раздел обновлений,
или `/opt/d2k/boot/d2k-service-adapter --root /opt/d2k service check`.

## Если что-то пошло не так

**`publish` упал посреди загрузки.** Канал не тронут, роутеры ничего не
видят. Черновик релиза с этим тегом удалите на GitHub и запустите workflow
ещё раз с **новым** номером (`release_id`), а не тем же.

**`publish` упал после загрузки, до перестановки канала.** Релиз
опубликован, но канал смотрит на прежний. Повторный запуск с тем же
`release_id` откажет (номер занят); выпустите следующий номер. Вреда
нет: роутеры берут только то, на что указывает `stable.json`.

**Actions не работает.** Ручного пути публикации нет и не проверялся.
Подождите; канал переживёт до 7 суток простоя.

**Пользователь сообщает, что обновление откатилось.** В панели видны
последний итог установки и карантин с причиной. Подробного журнала
обновлятора на роутере нет — его вывод сейчас никуда не пишется.
