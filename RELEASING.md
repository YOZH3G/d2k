# Как выходит релиз D2K

Руками релиз не выпускают. Каждый push в `main` проходит CI; если CI
зелёный и с прошлого релиза есть исправление или новое, релиз выходит сам.
Роутеры с автообновлением ставят его ночью 03:00–05:00 по своим часам или по
кнопке в панели.

## Когда релиз выходит

Правило — то же, что у semantic-release и release-please (Conventional
Commits). Релиз выходит, если с прошлого релиза есть хотя бы один коммит:

- `fix:` — исправление;
- `feat:` — новое;
- `perf:` — скорость;
- любой тип с `!` (`refactor!:`) или со строкой `BREAKING CHANGE:` в теле.

Составной тип считается, если в нём есть одна из этих частей:
`docs+fix:`. Коммиты `ci:`, `test:`, `docs:`, `build:`, `refactor:` сами
релиз не выпускают: роутер их не видит. Они уходят со следующим релизом.

Правило — в `scripts/release-plan.sh`, его тест — `scripts/test-release-plan.sh`.

Подпись коммита — это описание релиза. Панель покажет список `fix`/`feat`
с прошлого релиза. Пишите подпись так, чтобы человек понял, что изменилось.

## Как это идёт

```
push в main → CI (ci.yml) → ci-ok зелёный → release.yml:
  plan     есть fix/feat с прошлого релиза? нет — стоп, ничего не собирается
  build    девять арок параллельно, у каждой проверки под QEMU
  publish  архивы, latest.json, подпись Ed25519, черновик → публикация
```

Новый push в `main`, пока идёт CI, отменяет прежний запуск вместе с
релизом: релиз выпустит запуск нового коммита. Публикация проверяет, что
`main` ещё стоит на этом коммите. Если `main` ушёл, релиз не выходит, а в
журнале запуска есть notice.

### Ручной запуск

GitHub → **Actions** → **D2K release** → **Run workflow**, ветка `main`.
Нужен один раз: выпустить `main` сейчас, хотя `fix`/`feat` нет. В поле «Что
изменилось» можно вписать текст для панели. Коммит, у которого релиз уже
есть, второй раз не выпускается.

### Почему не PAT и не тег руками

`GITHUB_TOKEN` никогда не получает право `workflows` (правило GitHub, не
настройка). Поэтому GitHub не даёт ему поставить тег на коммит, у которого
`.github/workflows` отличаются от `main`: `HTTP 403: Resource not accessible
by integration`. 12.10.2026 релиз упал ровно так: пока он собирался, в
`main` пришёл коммит с правкой `ci.yml`. Личный токен с правом `workflow`
этот запрет обходит, но это долгоживущий секрет с правами владельца.
Релизу он не нужен: коммит, с которого `main` ушёл, всё равно устарел.

### Что делает workflow (`.github/workflows/release.yml`)

1. `plan` решает, выходит ли релиз, и даёт ему номер
   `d2k-<дата>-<время>-<коммит>` и описание.
2. `build` собирает `d2kd`, `d2kc`, `d2kpanel`, `d2ktg` девяти арок
   параллельно (`scripts/build-router.sh`) и гоняет их под QEMU
   (`scripts/check-router-builds.sh`). Кэша нет: Zig скачивается и
   сверяется по SHA-256, OpenSSL собирается из исходников. Подписанный
   выпуск не собирают тем, что оставил другой запуск.
3. `publish` упаковывает `d2k-<арка>.tar.gz` (`scripts/package-release.sh`):
   бинарники арки, `files/`, страницы панели и установщик
   `scripts/install.sh` — то же, что ставит ручная установка.
4. Пишет `latest.json` (номер, версия, описание, sha256 каждого архива) и
   подписывает его ключом Ed25519 из окружения `d2k-signing`. Подпись сразу
   проверяется ключом, закреплённым в `files/d2k-update.sh`.
5. Создаёт черновик релиза со всеми файлами, затем одним шагом делает его
   публичным и последним (latest). У черновика нет тега и ссылки на
   скачивание: роутер не увидит релиз без части файлов. Черновики `d2k-*`,
   оставшиеся от отменённых запусков, публикация удаляет.

### Что делает роутер (`files/d2k-update.sh`)

1. Берёт `releases/latest/download/latest.json` и `.sig`, проверяет подпись
   закреплённым ключом. Не сошлась — ничего не ставит.
2. Номер совпадает с установленным (`/opt/d2k/release-id`) — ничего не
   делает.
3. Скачивает архив своей арки, сверяет sha256 с подписанным `latest.json`.
4. Сохраняет текущие бинарники, скрипты, панель и `config` в
   `/opt/d2k/.update/previous.tar`.
5. Запускает установщик из архива (`D2K_LOCAL`), он останавливает и
   запускает службу. Затем минуту ждёт и проверяет, что датапат,
   контроллер и панель живы.
6. Успех — копия удаляется: на роутере остаётся только новая версия.
   Отказ — копия возвращается, служба перезапускается, выпуск помечается
   плохим: ночью он больше не ставится, вручную из панели — можно.

Журнал — `/opt/d2k/log/update.log`, состояние для панели —
`/opt/d2k/state/update.json`. Ночная установка выключается тумблером в
панели (`AUTOUPDATE=0` в `config`): тогда ночью только проверка.

## Правила

**Выпуск не переиздаётся.** Нашли дефект — выпускайте следующий. Роутер,
на котором выпуск не прошёл проверку, сам вернул прежнюю версию.

**`config` и каталог переживают обновление.** Установщик не трогает
существующий `config` и `state/`. Новые ключи конфигурации добавляйте так,
чтобы их отсутствие означало прежнее поведение.

**Канал один — выпуск.** Ручная установка из README и ночное обновление
ставят один и тот же подписанный архив: `scripts/install.sh` по умолчанию
проверяет подпись перечня, сверяет sha256 архива своей арки и запускает
установщик ИЗ архива. Поэтому новая установка не бывает старее обновлённого
роутера, и `builds/` в репозитории на роутеры не попадает.

До 14.10.2026 ручная установка брала бинарники из `builds/` ветки `main`, а
их обновлял человек. 13.10 это дало движок от 12.10 под службу и страницы
панели от 13.10; обновлять каталог сборки вместе с кодом больше не нужно, а
коммитить его из CI не надо тем более — полный комплект весит 110 МБ, то есть
столько же новых объектов в истории на каждый выпуск.

Два других источника:

- `D2K_LOCAL=каталог` — уже распакованный комплект. Так ставит
  `files/d2k-update.sh`, так же проверяется установка в лаборатории
  (`scripts/lab-install.sh`).
- `D2K_SOURCE=ref` — файлы ветки по `raw.githubusercontent` и бинарники из
  `builds/` этой ветки. Путь разработчика: подписи нет, свежесть `builds/`
  обеспечивает человек.

## Ключ подписи

Ed25519. Закрытая часть:

- на машине владельца — `~/.ssh/d2k_release_signing_ed25519.pem` (0600),
  открытая — рядом, `…pub.hex`;
- на GitHub — секрет `D2K_ED25519_PRIVATE_KEY` окружения `d2k-signing`.

Открытая часть — переменная репозитория `D2K_SIGNING_PUBLIC_KEY` и строка
`KEY=` в обоих скриптах, которые ставят выпуск: `files/d2k-update.sh` ночью
и `scripts/install.sh` рукой. Workflow проверяет, что все три совпадают: ключ,
которому верит только один из них, оставил бы половину роутеров без установки.
В репозиторий закрытый ключ не кладётся никогда.

Ключ лежит в секрете Actions: захват репозитория с доступом к окружению
`d2k-signing` даёт и подпись. Строже — обязательное подтверждение владельцем
(Settings → Environments → `d2k-signing` → Required reviewers).

**Потеря ключа** — роутеры больше не примут ни одного выпуска; поможет
только ручная переустановка с новым ключом в `d2k-update.sh`. Храните копию.

## Проверка

Перед выпуском, если менялись `files/`, установщик или обновление:

```sh
node scripts/test-update.cjs     # подпись, установка, возврат, тумблер
sh scripts/check.sh              # всё остальное
```

После выпуска:

```sh
curl -fsSL https://github.com/necronicle/d2k/releases/latest/download/latest.json
```

показывает новый `release_id`. На роутере — кнопка «Проверить» в разделе
«Обновления» панели или `/opt/d2k/d2k-update.sh check`.

## Если что-то пошло не так

**Workflow упал до публикации** — релиза нет, роутеры ничего не видят.
Исправьте и запустите снова.

**Пользователь пишет, что обновление не встало** — в панели виден итог и
причина; подробности в `/opt/d2k/log/update.log`. Прежняя версия к этому
моменту уже возвращена. Если возврат тоже не удался, копия лежит в
`/opt/d2k/.update/previous.tar` (распаковывается в `/`), и это сказано в
журнале.
