# Идентичность установки между перезапусками

Исходная ревизия: `1b0abe3`, ветка `main`. Это промежуточный шаг общей
живой приёмки, не исправление полевого остатка fast-torrent и не доказательство
открытия сайтов. Поле, роутер и production-бинарники не изменялись.

## Воспроизведение и изменение

Две последовательно созданные таблицы с первой установкой одного и того же
плана возвращали одинаковый `d2k_binding_context`: generation=1 и одинаковые
kind/family/shape/temporary. Старое событие нельзя отличить от нового по этому
контексту. Новый тест `test_plans` падает на исходном коде: «restart reused
complete installation identity» (`/tmp/d2k-binding-red.log`, один CHECK).

Таблица получает 128-битный случайный epoch на время своей жизни. Он вместе
с поколением копируется в существующие снимки Session/track/journal и в
APPLIED/REFUSED. Это метаданные; сериализованный packet program и код
производства пакетов не меняются. Если entropy недоступна/неполна, идентичность
остаётся неизвестной; исполнения пакетов это не запрещает. Никакого fallback
на PID, адрес памяти или часы нет. Коллизия случайных 128 бит теоретически
возможна; гарантии монотонного глобального счётчика здесь не заявляются.

Control v16 добавляет 16 байт epoch к прежнему 20-байтному хвосту исполнения.
Смешанная пара версий отвергается при приветствии. Проверяются обе судьбы
APPLIED/REFUSED, усечённые хвосты, исходный снимок при позднем pump и настоящий
путь Session → journal → control socket → link. При отсутствии entropy тест
проверяет нулевой контекст и доступность самого плана.

Ревью обнаружило соседний старый дефект: runtime сообщал wire=13 при control=15,
из-за чего `d2kc --self-check` уже не проходил. Новый CHECK в
`test_d2kc_proto` воспроизвёл отказ (`/tmp/d2k-runtime-wire-red.log`). Теперь
`runtime/d2k_protocol.h` — единственное определение версии для handshake,
CLI и health. Makefile-зависимости всех runtime-потребителей обновлены.
JS-тест handshake читает новую версию отдельно от определения события,
сохраняя возможность читать старые release fixtures.

Контроль старого кода без checkout и stale-объектников: `plans.c` из
`1b0abe3` скомпилирован заново в отдельный `/tmp`-бинарник с окончательным
`test_plans`. Exit 1, два CHECK: restart identity и entropy failure
(`/tmp/d2k-binding-baseline-fresh.log`). Текущие `test_plans`, `test_session`,
`test_ctl`, `test_link` проходят. Равенство байтов исполнения этим изменением
не переопределяется: epoch отсутствует в сериализованном packet program.

## Что это ещё не закрывает

Следующий описанный ниже шаг реализован в [HTTP live binding](2026-10-11-http-live-binding.md).
Этот раздел фиксирует состояние на момент ff5decd.

HTTP ACK установки пока возвращает корреляцию команды, но не контекст
установленной привязки. `http80` сохраняет execution/plan/trial/request, но
не binding; HTTP_PORTAL также не несёт его. `httpsearch_bound_failure`
по-прежнему опирается на hash и время. Его удаление по имени не имеет
условия «снять только это поколение». Поэтому новый epoch сам по себе
ещё не защищает HTTP-отзыв и не превращает зонд в живую приёмку.

Конкретное окно ошибки для следующего регресса: контроллер записывает
`installed_ms` после успешной записи SET_NAME в сокет, до ACK датапата.
Запрос ещё под старой привязкой может начаться после этой отметки; его
ответ-портал приходит после фактической переустановки того же hash. Проверка
времени пропускает этот ответ как принадлежащий новой установке. Сравнение
неизменяемого binding и условное удаление закрывают обе стороны этой гонки.

Следующий цельный шаг:

1. Коррелированный ACK SET_NAME возвращает фактически установленный binding;
   все пути install/restore/resync сохраняют только свой ACK.
2. Завершённое исполнение конкретного HTTP-запроса сохраняет неизменяемый
   binding; ответ/портал несёт именно его, а не текущую запись таблицы.
3. Контроллер сопоставляет цель, семейство, форму, постоянный name-ключ,
   epoch, generation, plan и execution. Удаление атомарно проверяет ожидаемую
   привязку на стороне таблицы; старое событие не снимает новую установку.
4. Регрессы: тот же hash после переустановки/рестарта, поздний портал,
   неизвестный контекст, чужая форма/семейство, повтор события; действительный
   портал снимает только свою привязку. Проверять фактический путь d2kd/control,
   а не только фальшивые callbacks измерителя.

Даже после этого ACK/APPLIED не станет PASS. Положительный HTTP-критерий
потребует полноты каждого ответа и отсутствия портала на каждом запросе;
TLS RX и QUIC требуют собственных наблюдаемых сигналов. Полевое подтверждение
и сдвиг таблицы «замер/перебор/время» остаются за координатором.
