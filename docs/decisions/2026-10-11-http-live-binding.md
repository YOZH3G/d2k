# HTTP: привязать живой отказ к фактической установке

База: `ff5decd`, ветка `main`. Это продолжение общей живой приёмки;
оно закрывает владение отрицательным HTTP-свидетельством, а не доказывает
снятие портала fast-torrent. Роутер, поле и production-бинарники не менялись.

## Причина и изменение

Раньше `httpsearch` считал момент записи SET_NAME в сокет границей установки.
Запрос под старой привязкой мог начаться после этой отметки; поздний портал
с тем же plan hash принимался за отказ новой установки. Удаление по имени
могло снять уже заменённый план. Время и hash не идентифицируют опыт.

Control v17 добавляет две команды. SET_NAME_BOUND возвращает в коррелированном
ACK фактический контекст установки: epoch таблицы, generation, тип ключа,
семейство, форму и временность. DEL_NAME_BOUND атомарно сравнивает этот
контекст с записью перед удалением. Устаревшая команда — безопасный no-op.
Контроллер и датапат требуют одной версии протокола; обновляются парой.

Завершённое исполнение конкретного HTTP-запроса сохраняет этот неизменяемый
контекст. HTTP_PORTAL переносит его через production encoder и Unix control
socket в production consumer контроллера. Отказ постоянного плана принимается
только при совпадении собственного ACK, цели, семейства, формы HTTP, name-ключа,
поколения/epoch и plan ID; требуются ненулевой execution ID и отсутствие trial ID.
Неподтверждённая переустановка блокирует атрибуцию. Время остаётся диагностикой.

Matched NACK сохраняет последнюю достоверную установку, но не заимствует
контекст из отказа. Если ранее была ещё одна неподтверждённая переустановка,
старое владение уже неизвестно: NACK не восстанавливает его. Поздний собственный
ACK завершает отложенный отзыв. Неудачная запись удаления повторяется при resync
с тем же точным контекстом; новая привязка от этого не страдает.

Изменены `core/httpsearch.c`, `link.c`, `d2kc.c` и их заголовки;
`datapath/http80.c`, `ctlsrv.c`, `plans.c`, `d2kd.c` и заголовки;
общая версия `runtime/d2k_protocol.h`. Производство пакетов не менялось:
HTTP по-прежнему использует единый Plan/Session/wire engine.

## Воспроизведение и регрессы

До правки на ff5decd новый CHECK старого API воспроизвёл окно SET до ACK:
`unacknowledged replacement accepted old live failure`.
`make -C core test-httpsearch` — exit 2, один CHECK,
`/tmp/d2k-http-identity-red.log`. После изменения API окончательный файл теста
не заявляется компилируемым без адаптации на старой ревизии.

Во время ревью отдельно воспроизведены и исправлены:

- отзыв до ACK: два CHECK, `/tmp/d2k-http-pending-revoke-red.log`;
- повтор условного удаления после ошибки записи: десять CHECK в IPv4/IPv6,
  `/tmp/d2k-http-delete-retry-red.log`;
- ACK A → SET B → NACK B: два CHECK, `/tmp/d2k-http-nack-owner-red.log`;
- две неподтверждённые установки → NACK: один CHECK,
  `/tmp/d2k-http-overlap-red.log`.

`test_httpsearch` проверяет состояния ACK/NACK/перекрытия/отзыва.
`test_link` проверяет независимый wire fixture ACK, endian, усечения и теги.
`test_http80` проверяет неизменяемый снимок второго запроса и ретрансляцию первого.
`test_http_live` проводит установку, ACK, событие и условное удаление через
реальный control socket, production encoder/consumer и таблицу планов;
исполнение запросов — реальный Session с полным сравнением пакетов IPv4/IPv6.
Сигнал портала в этом control-тесте — детерминированная фикстура, не полевой pcap.
Пакетный HTTP-monitor проверяется отдельно. Это не полный NFQUEUE field replay.

Дополнительная проверка чувствительности: свежий отдельный бинарник с заменой
точного сравнения binding в `plans.c` на проверку лишь известности binding.
Компиляция exit 0, тест exit 1, 22 накопленных CHECK (первичный — stale delete
снял замену, остальные следствия). `/tmp/d2k-http-cas-mutation.log`.
Рабочее дерево и его объектники для мутации не изменялись.

Окончательные целевые тесты проходят:
`make -C core test-httpsearch test-http-live test-link` и
`make -C datapath test-http80 test-ctl test-plans` — exit 0.
Логи `/tmp/d2k-http-identity-final-targeted.log`,
`/tmp/d2k-http-binding-dp-final-target.log`.

## Граница результата и следующий шаг

ACK/APPLIED/COMPLETE по-прежнему не являются PASS. Положительная HTTP-приёмка
требует полноты каждого ответа и отсутствия портала для каждого запроса.
Потерянный или вытесненный ACK может оставить фактическую установку с неизвестным
владением; здесь нет ни ложного PASS, ни широкого удаления. Полное восстановление
такого состояния — отдельный незакрытый случай.

Этот шаг не нашёл новый обход keep-alive и не подтвердил открытие fast-torrent.
Следующий шаг — учёт каждого живого HTTP-запроса/ответа и проверка конкретного
повторного запроса из поля под измеренным воздействием. Для фикстуры нужен полный
pcap/pcapng в обе стороны от SYN до завершения keep-alive, с payload и отметкой
LAN/WAN, плюс совпадающий журнал, ревизия и plan ID. При обезличивании сохранять
длины, SEQ/ACK и корректные checksums. Сам захват выполняет координатор.

Для следующего регресса важны две независимые границы наблюдения:
`datapath/http80.c` переходит из REQUEST в IDLE уже на первом сегменте ответа;
`files/S99d2k` после начального окна направляет в NFQUEUE только HTTP PSH.
Это не покрытие всех байтов тела. Положительный сигнал нельзя строить ни из
состояния IDLE, ни из отсутствия HTTP_PORTAL: пропуск сегмента/заголовка,
неизвестное framing или вытеснение состояния должны сохранять unknown.
Чтение полного тела собственного зонда в `core/verify.c` не доказывает полноту
пассивного наблюдения. Правила сети в этом шаге не изменялись и не применялись.

mailsuite, порядок измерений QUIC, постоянный транспортный cooldown и сводка
целого прогона остаются в общей задаче. Их полевой результат этим коммитом
не переоценивается. Критерий владельца — сдвиг следующей таблицы
«замер/перебор/время» и измеримый сигнал класса на живом применённом потоке.
