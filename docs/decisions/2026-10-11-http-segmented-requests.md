# HTTP keep-alive: граница запроса не зависит от сегментации заголовков

База cabe6c4, main. Продолжение
[trial proof](2026-10-11-scheduler-trial-proof.md) и задачи живой приёмки.
Поле владельца: fast-torrent получает первый полный ответ, а следующий GET
на том же соединении — портал. Приведённое ниже — отдельное локальное
воспроизведение дефекта; именно такую сегментацию в поле пока не проверяли.

## Причина

Session применял план при полном Host в первом сегменте, но при отсутствии
конца заголовков навсегда терял границу следующего запроса. HTTP-наблюдатель
отвергал первый запрос ещё раньше: его прежний GET/HEAD helper требовал весь
запрос в одном сегменте. Получалось два пробела: следующий запрос не получал
план и его ответ не мог участвовать в живой приёмке.

## Исправление

`d2k_http_request_stream.h` — общий инкрементальный разбор framing для
Session, HTTP-наблюдателя и прежнего stateless `d2k_http_request`.
Сохраняет только состояние поля и численную длину: Cookie/другие значения
не накапливаются в памяти. Выделений памяти на пакетном пути нет. Локальное сравнение sizeof(d2k_flow)
со старым заголовком: 2864 → 2920 байт (+56); это размер текущей macOS-сборки,
а не замер памяти или CPU на роутере.

Полный request line и Host по-прежнему должны находиться в первом сегменте.
После них последовательные продолжения заголовков восстанавливают границу
`конец заголовков + Content-Length`. Следующий запрос с начала сегмента на
этой границе получает тот же план, как первый. Целая старая ретрансляция
не становится новым запросом. CL-дубли, негодная длина, TE, Upgrade,
obs-fold, пропуск/частичное перекрытие заголовков и конвейер через границу
не дают выдуманного следующего запроса.

Наблюдатель узнаёт GET/HEAD по request line/Host, хранит execution ID и
binding с первого сегмента, затем завершает framing общим parser. Полный
ответ и портал следующего запроса относятся к своим request_no/execution.
Положительный ответ требует завершённого, однозначного входного запроса.
Перенаправление на подтверждённый HTTPS также требует законченного запроса
без тела; прежний публичный `d2k_httpup_request_safe` не ослаблен.

Изменился диагностический счётчик `requests`: распознанный request line/Host
с ожидаемым хвостом Cookie теперь учитывается как наблюдаемый запрос, а не
`unparsed`. Это не счётчик успешных ответов.

## Красный → зелёный и равенство исполнения

- Перед исправлением штатный `core/test_http_live` провалил оба IPv4/IPv6
  случая второго запроса, `datapath/test_http80` — четыре случая ответа/
  портала. Логи `/tmp/d2k-http-segment-{live,observer}-red.log`.
- Расширенный test_http_live со свежей компиляцией старых session.c/http80.c
  из cabe6c4 в отдельном временном каталоге: exit 1, восемь CHECK. Checkout
  и старые объектники не используются. `/tmp/d2k-http-segment-baseline.log`.
- Новый live-regress: IPv4/IPv6 × пробный/постоянный план × Cookie, разрез
  Content-Length/тела, CL-дубли, TE и потерянный байт. Пакеты строит настоящий
  Session; полные выходные пакеты и интервалы trial/permanent сравниваются.
  После исправления — exit 0. `--diverge` повреждает пакет и даёт exit 1
  (12 CHECK), `/tmp/d2k-http-segment-diverge.log`.
- Наблюдатель проверяет полный первый ответ и портал второго, отдельные
  execution ID и binding. Stream-тест перебирает каждую точку разреза,
  повтор, wrap TCP seq, CL/TE/Upgrade/obs-fold/дубли Host, gap/overlap.
- Старый test_http_hello требовал пропустить второй запрос после разрезанных
  заголовков. Его ожидание заменено на применение после доказанной границы;
  проверки chunked, конвейера и остальных неизвестных границ сохранены.

Новый сборщик пакетов не введён. Runtime-проверка сравнивает полные пакеты,
а не только описание плана или число посылок.

## Граница результата и поле

Это не доказательство открытия fast-torrent и не новое воздействие против
портала. Если портал появится после COMPLETE второго запроса, исправление
framing само по себе его не снимает: воздействие нужно заново измерять в
этом контексте. Для координатора: pcap/pcapng обоих направлений от SYN,
полная длина пакетов, точка LAN/WAN, журнал и ревизия. Сверить по каждому
GET границу, COMPLETE/SKIPPED, execution ID и полный ответ либо портал.

Разрезанный Host/request line, HTTP-конвейер внутри сегмента, chunked-тело
запроса и общая TLS/QUIC live-приёмка остаются отдельными незакрытыми случаями.
Mailsuite и общий QUIC замер данным изменением не закрываются. Роутер,
поле, браузеры и push не запускались; два dirty arm64-бинарника владельца
не менялись. Общая goal остаётся активной.
