# HTTP: составной Host/request line на реальном пути исполнения

База `4ef3c8b`, main. Продолжение
[границ сегментированных запросов](2026-10-11-http-segmented-requests.md).
Полевое основание — портал на следующем keep-alive GET fast-torrent.
Конкретный разрез Host/request line воспроизведён локально: его наличие
в полевом pcap владельца пока не установлено. Это исправление достижимости
исполнителя, не доказательство нового воздействия против портала.

## Причина и решение

До исправления поток проходил через три несовместимых условия:

1. Session разрешал удержание только TLS; первый фрагмент HTTP уходил как есть.
2. Даже при разрешении удержания capture проверял TLS-заголовок, не HTTP.
3. Якорь сборки всегда был SYN+1, хотя второй HTTP-запрос начинается позднее.
   HTTP-наблюдатель работал до удержания и терял запрос с неполным Host.

Общий capture сохраняет единственный сборщик байтов по TCP seq, проверки
перекрытий и ограничения. Добавлен callback готовности: прежняя TLS-проверка
или существующий HTTP parser. Это сборка входа, а не второй генератор
пакетов обхода. HTTP-ветка включается только для правдоподобного начала
метода на наблюдённой границе либо уже распознанного HTTP-потока. Порт 80
сам по себе не выбирает HTTP; TLS на нём сохраняет прежний путь, включая
хвост, пришедший первым.

Prefilter требует установленного HTTP-плана для family и контекста
source port (пробный/постоянный). Полный Host затем по-прежнему проверяет
Session: prefilter не даёт права применить чужой план. Для следующего
запроса используется доказанная framing-граница предыдущего. Таймаут или
смена таблицы отпускают оригиналы и инвалидируют границу неполного HTTP.

В d2kd наблюдение HTTP перенесено после owning hold. WAIT не поступает ни
наблюдателю, ни Session; READY даёт обоим одну собранную картину запроса.
Этот синтетический пакет **не отправляется**. Вердикт относится к точным
ID удержанных оригиналов. Для fake-badsum-whole на провод уходят приманка
и два исходных сегмента, а не приманка и склеенный вход.

## Границы и следующий шаг

Нет доказательства снятия портала после COMPLETE: это устанавливает поле.
Нужны pcap/pcapng обоих направлений от SYN с полной длиной, отметкой LAN/WAN,
журналом и ревизией. По каждому GET сопоставить границу, исполнение,
полный ответ либо 302→lawfilter. Если портал приходит после COMPLETE,
повтор того же fake на новых запросах недостаточен — требуется измерять
воздействие именно после успешного первого ответа на той же связи.

Начальный HTTP-хвост, пришедший прежде метода, не классифицируется HTTP
по одному порту. HTTP-конвейер внутри сегмента, chunked request body,
граница внутри сегмента остаются неизвестными; успешный исход им не
приписывается. Удержание по-прежнему ограничено существующими 100 мс,
размером capture/слота и количеством ID. Оно может ожидать хвост, который
ядро отправителя не выпускает до ACK головы: тогда fail-open и unknown,
а не успех. Пробный прогон полных пакетов в локальном тесте не доказывает
доставку хвоста реальным ядром/NFQUEUE.

Замечание ревью без блокировки: timeout/revision regression явно вызывает
flush до следующего candidate. Истечение внутри hold_feed после вычисления
candidate может дать лишнее удержание; callback инвалидирует HTTP-границу,
поэтому доказанного ложного исполнения нет. Это отдельная граница общей
механики удержания, не основание объявлять приёмку полной.

Следующий HTTP-шаг — проверить повторную приёмку того же кандидата после
связанного живого отказа. В текущем httpsearch.c build_cands повторно пробует
own->key, включая revoked-гипотезу; confirmed снова снимает revoked после
зондов. Повторный зонд уже отправляет `/`, затем сохранённый repeat_path на
том же соединении, но не воспроизводит весь браузерный запрос/историю.
Нужен регресс «живой отказ → короткий воспроизводитель снова проходит» и
явное сохранение границы этого доказательства. Сам по себе повторный успех
зонда не доказывает снятие живого отказа. Это аудит следующего шага, а не
изменённое поведение текущего коммита. Общие исходы поиска/очереди и
live-критерий TLS/QUIC остаются в единой задаче.
Mailsuite, неуспешный QUIC-поиск и таблица полного эпизода данным коммитом
не закрыты. Общая goal остаётся активной. Роутер, поле, браузеры и push
не запускались; dirty arm64-бинарники владельца сохранены.
