# HTTP: исполнение каждого запроса и идентичность опыта

Основание: поле fast-torrent после bbd8dca, активная goal после прогона j.
Исходная ревизия b16071d, main. Поле, роутер и push не запускались.

## Два воспроизведённых дефекта

1. `httpsearch.c` принимал APPLIED по одному plan ID. Одного такого события
   хватало для двух полностью прочитанных HTTP-ответов на keep-alive связи.
   Счётчик полных ответов не доказывал исполнение обхода второго запроса.
2. Настоящий Session/control тест показал, что SET_NAME_PROBE возвращал
   trial ID в ACK, но таблица именных планов его не сохраняла. TCP/HTTP
   `plan_handed_off` получал NULL и публиковал APPLIED с нулевым trial ID.
   Сверка только plan ID скрывала эту потерю контекста.

## Изменение

HTTP-зонд возвращает число отправленных запросов и фактические адрес/порт
своего соединённого сокета. Контроллер принимает отдельные завершения
исполнения для каждого отправленного запроса: совпадают trial, plan, TCP,
семейство, адрес цели/80, локальный сокет и временная именная HTTP-привязка
с epoch/generation. Повтор одного execution ID не увеличивает доказательство.
Позднее событие после удаления временной записи проверяется по сохранённому
контексту опыта, а не по текущей таблице. Недостаток доказательств означает
«кандидат не судим», а не успешное снятие блока.

Именная временная установка сохраняет trial ID как metadata привязки.
Общий `plan_handed_off` копирует его в execution snapshot; журнал и control
уже умеют передавать его. При rebind metadata сбрасывается. Legacy-вызовы
с нулевым trial по-прежнему устанавливаются, но остаются неизвестным
доказательством и не подтверждают строгий HTTP-опыт.

Формат control остаётся v18; формат плана и код производства пакетов не
изменены. При развёртывании нужны обе новые службы: старый d2kd не выдаёт
контроллеру необходимую идентичность HTTP-опыта.

## Регрессы и границы доказательства

- `core/test_httpsearch.c`: два ответа при единственном исполнении не
  публикуют план. На исходном httpsearch.c/header b16071d, свежая компиляция
  в отдельном временном каталоге: exit 1, один CHECK. Лог
  `/tmp/d2k-http-execution-baseline.log`.
- Матрица IPv4/IPv6 отвергает чужие trial/plan/адрес/порт/транспорт/семейство,
  неизвестную и другую привязку, дубликат execution, несовпадение фактического
  сокета. Проверяет позднее второе событие и обратную канонизацию endpoints.
- `core/test_http_live.c`: настоящие SET_NAME_PROBE → Session → завершение
  raw sends **и NF verdict** → журнал → Unix control → HTTP-приёмка.
  Два полных ответа без второго события не публикуют план; после всех
  завершений двух опытов публикация разрешена. На свежесобранном старом
  Session b16071d этот тест даёт exit 1 и четыре CHECK: trial потерян.
  Лог `/tmp/d2k-http-execution-runtime-red.log`. С правкой IPv4/IPv6 проходят.
  Отдельно сохраняется работоспособность legacy-установки с нулевым trial.
- HTTP-ответы в Session/control тесте — фикстуры; фактический getsockname
  зонда проверяется отдельным loopback-тестом. Физический NFQUEUE/raw send
  и браузер не проверялись. Существующий full-packet memcmp сравнивает
  временное и постоянное исполнение; новый сборщик байтов не добавлен.

## Что это не закрывает

Положительный результат остаётся подтверждением конкретного зонда, не
всех будущих клиентских потоков. Живая HTTP-приёмка полного ответа и
отзыв по порталу требуют поля (предыдущая правка 8d2da51). Нет свидетельства,
что fake-badsum снимает портал fast-torrent на каждом браузерном запросе.
Нужны предложенные владельцем pcap/pcapng обеих сторон от SYN с полным
payload, пометкой LAN/WAN, журналом и ревизией. Первая цель следующего
разбора — сопоставить каждый запрос, его COMPLETE/SKIPPED и полный ответ
либо вставку, затем воспроизвести конкретное различие входа/исполнения.

Mailsuite, дерево QUIC до fallback, справедливость очереди, остаточный
cooldown и полная метрика эпизода остаются в активной goal. Локальные
регрессы не заменяют сдвиг таблицы замер/перебор/время следующего прогона.

Следующая граница общего планировщика: `sched.c:applied_of_candidate`
сверяет trial только для адресной цели; `T_VERIFY_WAIT` в `on_applied`
сверяет лишь flow/plan. Ранний буфер хранит только flowkey и теряет binding
и execution. Для именных кандидатов нужно связать подтверждение с
`trial_ack_id`, сохранить полный execution snapshot и проверять его после
возврата verifier. Эта HTTP-правка предоставляет необходимый trial в
датапате, но общий scheduler ещё не переведён на такую приёмку. TLS/QUIC
шифруют приложение: живой RX-прогресс доказывает именно прогресс/пройденную
границу измеренного обрыва, а не неизвестный HTTP-статус или полную страницу.

В частности, `session.c` увеличивает fwd/rev_data_pkts на каждый пакет с
payload, а rev_bytes — на IP total; `ct_tcp_flow` добавляет оценку unseen
conntrack packets. Повторные сегменты не дедуплицируются по TCP sequence.
Эти счётчики служат подозрению о stall, не положительному доказательству
уникального объёма RX. Для последнего нужен отдельный учёт последовательности
и полноты наблюдения конкретного applied-потока.
