# QUIC уступает измерительный слот между вопросами

База `047609f`, main. Полевое основание — прогон j на bbd8dca:
QUIC-поиск занимал слоты на 42–51 опыт, TCP ждал. Прежняя очередь могла
выбрать TCP только после окончания всего worker. Приоритет только среди
ещё не запущенных задач этого не решал.

## Устройство

Пауза допустима на границе `quicarms.c:ask_q`, до отправки следующего
вопроса. Фильтр 3/3 и data-stage одного вопроса неделимы; открытая QUIC-связь
не ставится на паузу. Thread-local приёмник scheduler связывает hook с
конкретной задачей. Вне scheduler hook не меняет поведение измерителя.

Worker сохраняет стек, ответы, адресный курсор, mark и byte program. Он
сообщает waiting под mutex и ждёт condition variable. Главный цикл только
после этого помечает задачу parked и освобождает измерительный слот.
При возобновлении слот резервируется до пробуждения. Это не новый поиск,
не сетевой NO и не FLAKY. Предельное число ожидающих учитывает parked,
так что сохранённые worker не обходят существующее ограничение очереди.

TCP получает свободный слот раньше новых QUIC. После одного допуска TCP
сохранённый QUIC получает очередь на следующий свободный слот даже при
новых TCP в очереди: бесконечного приоритета TCP нет. Между запусками
сохранён прежний pacing 250 мс. Количество вопросов и критерии не урезаны.

Фактическое время ожидания исключается из внутреннего Run budget через
существующий spent callback; модельное время парковки — из внешнего
started_ms/lifetime. Полное время эпизода не скрывается, ожидание прибавляется
к report_queue_ms. join_worker выставляет stop и будит condition variable
до join. Пауза не меняет trial, постоянный план или сетевой результат.

Новых отправителей/пакетных преобразований нет. Весь поиск с паузой даёт
тот же результат/trace, что и без неё; общий runtime gate продолжает
сравнивать полные пакеты замера и production Session.

## Доказательства

- Новый `test_sched_quic_yield` до правки: 2 CHECK, make exit 2,
  `/tmp/d2k-quic-yield-red.log`. Следующий QUIC-вопрос начинался до допуска
  ожидающего TCP, свободного слота TCP не получал.
- После: занятые слоты, неделимость filter/data-stage, удержание TCP-слота,
  возобновление без повторных вопросов, долгий parked, очередь новых TCP,
  отсутствие паузы без конкурента, отмена до/после parked.
- `test_quic_strategy` отдельно проверяет прибавление времени паузы до
  проверки сетевого бюджета и отмену без посылок.
- Возврат старой внешней lifetime-проверки в отдельной временной сборке:
  compile exit 0, test exit 1, четыре CHECK;
  `/tmp/d2k-quic-yield-lifetime-red.log`. Рабочее дерево не откатывалось.
- Waiting до регистрации parked проверяется до общего deadline. Новый
  пограничный регресс сначала дал 1 CHECK, make exit 2:
  `/tmp/d2k-quic-yield-waiting-red.log`. Время входа в ожидание берётся
  из последнего model-clock snapshot под mutex, а не из времени поздней
  регистрации. Отдельная проверка компенсации started_ms также упала:
  `/tmp/d2k-quic-yield-clock-red.log`; финальный вариант проходит оба.
- `san-sched-quic-yield` (ASan/UBSan) — exit 0:
  `/tmp/d2k-quic-yield-final-san.log`. Отдельная сборка того же теста и
  runtime с ThreadSanitizer — compile/test exit 0, без сообщений о гонках:
  `/tmp/d2k-quic-yield-tsan.log`. Это проверенные сценарии, не доказательство
  всех возможных interleaving или нагрузки роутера.
- Статическое read-only ревью выявило lifetime/starvation; замечания
  исправлены, повторный просмотр не нашёл important/blocker.

После дополнительного deadline-регресса финальный `core check` запущен в
отдельной локальной копии исходников (git archive `047609f` + текущий core
diff + новый тест). Все шесть изменённых файлов кода/тестов побайтно
совпадают с рабочим деревом. Это исключает смешивание объектников с уже
выполнявшейся первой проверкой; первый набор не прерывался.

## Границы

Это сокращает удержание слота ожидающему TCP, а не доказывает новый QUIC-обход.
Текущий вопрос должен закончиться; немедленного прерывания пакета или
открытого data-stage нет. База/direct/диагностический хвост QUIC пока не
уступают между своими вопросами — hook охватывает стратегию и запасную
лестницу, основную выявленную долгую часть. Физическое время улучшения,
нагрузка роутера и изменение таблицы прогона не измерены локальными тестами.

Сохранённый worker держит память стека до возобновления. Активные замеры
по-прежнему ограничены ресурсным лимитом, ожидающие — существующей ёмкостью
очереди, но фактический peak RSS/CPU нужно снять владельцу в поле. Порог
не менялся; дополнительных сетевых опытов ради планирования нет.

Координатору в следующем обычном прогоне: сопоставить строки уступки и
возобновления с началом TCP-поиска, измерить queue_ms/elapsed_ms и счётчики
зондов; проверить отсутствие повторов уже отвеченных QUIC-вопросов и
десятиминутного cooldown именно вследствие паузы. Исход текущего вопроса,
применение плана и критерий живого потока учитывать отдельно.

Итоговая метрика всего эпизода ещё не обобщена. В этой правке queue_ms
пополняется при возобновлении; ожидание отменённой parked-задачи пока видно
в общем elapsed_ms, но не выделено в queue_ms. Это следующий пункт учёта,
а не основание объявлять уменьшение общего времени по локальному тесту.

fast-torrent/mailsuite и приёмка всех живых классов этой правкой не закрыты.
Роутер, поле, браузеры и push не запускались.
