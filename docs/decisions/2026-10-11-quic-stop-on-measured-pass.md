# QUIC: первый полный измеренный кандидат завершает поиск

База `8d2da51`, main. Требование — D2K_SPEC §0.1: прошедший вопрос уже
доказывает приём в контексте замера; поиск на нём останавливается.
Это не отменяет последующего испытания плана и живой приёмки.

## Причина лишней работы

Полевой [прогон j](../field/2026-10-11m-run-j-measured-vs-fallback.md)
показал 42–51 опыт QUIC и занятую очередь. Аудит выявил два независимых
продолжения **уже успешного** поиска:

1. `quicarms.c:d2k_quic_original_arms` после успешной одиночной приманки
   продолжал варианты числа копий, затем TTL и контроль/формы фрагментации.
   `ask_q` уже проверил 3/3 и этап данных. При последующем локальном сбое
   mark кандидат мог стать FLAKY; при исчерпании свежих адресов получал
   incomplete, хотя сам рабочий опыт состоялся.
2. `quicprobe.c:classify_run` после возврата успешного arm запускал оставшиеся
   диагностические вопросы. Их ответы не требуются для принятия именно
   уже измеренного воздействия; ошибки снова влияли на общий mark.

Это не объяснение 13 полностью неуспешных прогонов. В них первого полного
кандидата не было, поэтому эта правка не сокращает их сама по себе.

## Изменение

Первое воздействие, принятое `ask_q`, немедленно становится результатом:
те же bytes/copies/TTL, без последующих усилений. При полном промахе
порядок оставшихся гипотез сохранён, произвольный предел зондов не добавлен.
Фильтр 3/3 без этапа данных в production не даёт раннего успеха.

После результата arm диагностический хвост пропускается только при
пригодном kind и последней записи trace с 3/3, PASS этапа данных и без
not_measured. Нулевой/неизмеренный arm, FLAKY и поиск без кандидата этого
условия не выполняют. Режим classify-only сохраняет диагностику.
Журнал поясняет: «кандидат прошёл этап данных — дальнейшие вопросы не нужны».

Новые wire-примитивы и отправители не добавлялись. Компилятор/исполнитель
общего UDP-плана прежний; меняется выбор точного уже проверенного варианта.
Победитель запасного поиска остаётся путём «перебор»: он не переименован
в «свойство» ради метрики.

## Воспроизведение и проверки

Новые регрессы до правки продукта:

- `test_quic_original_arms`: первый опыт 3/3 + data PASS, следующий дал бы
  ошибку mark; ожидается ровно один опыт, неизменённая одиночная приманка
  и достоверная метка. Три CHECK упали, make exit 2:
  `/tmp/d2k-quic-stop-red.log`.
- `test_quic_run_order`: после успешного вопроса остаточного разрешения
  больше не отправляются диагностические Initial. CHECK упал, make exit 2:
  `/tmp/d2k-quic-stop-run-red.log`.

После правки targeted original-arms/strategy/run-order прошли:
`/tmp/d2k-quic-stop-green.log`. Свежая отдельная компиляция старого
`quicarms.c` из `8d2da51` с новым тестом: compile 0, test 1,
`/tmp/d2k-quic-stop-baseline.log`; checkout/stale-объектники не использованы.

Runtime gate на текущем выборе кандидатов: `test_udp_runtime` — exit 0,
130 full-packet cases / 19 distinct actual questions. Тот же бинарник с
`--diverge` — exit 1: преднамеренное расхождение пакетов обнаруживается.
Логи `/tmp/d2k-quic-stop-runtime-green.log` и
`/tmp/d2k-quic-stop-runtime-mutant.log`. Это IPv4/IPv6, размеры и реальные
вопросы/выбранные планы в production executor с перехваченным sink;
физический провод роутера и браузер этим не проверены.
До раннего выхода было 198 cases / 53 questions: матрица автоматически
перехватывает отправляемые вопросы; исключённые последующие усиления
больше не генерируются. Сам comparator и тестовый источник вопросов не
менялись. Негативный gate дал 130 failures, а не ложный PASS.

Часть старых тестов требовала продолжения успешного поиска до TTL. Их
ожидания изменены явно, с проверкой точного первого кандидата и числа
вызовов. Первый полный core check обнаружил ещё два таких ожидания в
`test_quic_arm_data`; они обновлены. Негативные сценарии оставлены:
3/3 без рукопожатия/данных, CUT на втором H3-потоке, отсутствие свежих
адресов до результата, полностью неуспешная лестница и фрагментация.

## Граница и следующий шаг

Этот результат уменьшает лишнюю работу после успеха; миллисекунды поля
и сдвиг таблицы пока неизвестны. Критерий следующего прогона: после первого
полного кандидата отсутствуют дополнительные вопросы; выбранный план
совпадает с этим опытом; отдельно сохраняются время и результат живого
потока. Не объявлять зонд приложением.

Полностью неудачная лестница всё ещё может занимать слот до конца:
`sched.c:launch_or_queue` считает задачу целиком, `queued_pick` выбирает
лишь после освобождения слота. Переставить только ожидающие задачи
недостаточно, когда все слоты уже заняты. Следующий шаг очереди требует
уступки между опытами с сохранением курсора адресов, residual-контекста,
отвеченных вопросов и учёта активного времени; отмена и повтор с начала
повторят уже измеренное и не решат причину.

Для расширения измерения остаётся дерево из
[общего разбора](2026-10-11-measured-search-live-outcomes.md): пригодные
диагностические оси должны получить ту же data-stage и runtime-проверку
до fallback. Версия/порт не меняются незаметно в чужом клиенте.
HTTP fast-torrent, mailsuite и живая приёмка всех классов не закрыты.
Роутер, поле и push не затрагивались.
