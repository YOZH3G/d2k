# Планировщик: APPLIED относится к текущему опыту

Продолжение HTTP identity b15618b; исходная ревизия b15618b, main.
Предыдущий шаг сохранил trial ID именного плана в датапате. Здесь этот
идентификатор используется общей приёмкой кандидата TCP/QUIC.

## Воспроизведение и причина

`applied_of_candidate` проверял trial только у адресных целей. Ранний
APPLIED именной цели принимался по plan/target и затем связывался с flow
вернувшегося verifier. Поздняя ветка `T_VERIFY_WAIT` проверяла лишь
flow/plan, включая адресные цели. Поэтому совпавший поток и план позволяли
чужому либо нулевому trial подтвердить успешный зонд как свой опыт.

## Минимальное исправление

Обе ветки APPLIED требуют ненулевой идентификатор текущей установки:
`trial_ack_id` для name, `addr_probe_trial_id` для addr. Сверки плана,
семейства, транспорта и полного потока сохраняются. Установка следующего
кандидата по-прежнему обнуляет буфер ранних свидетельств.

Новые отправители, воздействия или критерии ответа приложения не вводятся.
Обработка REFUSED и диагностических property-вопросов не меняется: эта
правка относится к приёмке кандидата, а не ко всем видам control-событий.
Нужен d2kd как минимум b15618b: прежний именной путь терял trial ID.

## Регресс

`core/test_sched_trial.c` использует общий scheduler harness и публичные
события/команды. 36 случаев: IPv4/IPv6 × TCP name/QUIC name/QUIC addr ×
APPLIED до/после verifier × trial нулевой/чужой/свой. Сетевые ответы —
подменённые, цель — проверить решение планировщика и каталог, не провайдер.

Свежая компиляция старого `sched.c` b15618b в отдельном временном каталоге
с новой матрицей даёт exit 1 и 20 CHECK; корректные адресные ранние события
и положительные контроли не падают. Лог `/tmp/d2k-sched-trial-baseline.log`.
После правки матрица даёт exit 0, `/tmp/d2k-sched-trial-matrix.log`.
Старые тесты теперь получают trial вместе с plan ID из фактической команды
установки своего harness, а не генерируют идентичность из plan hash.
Отрицательный voice-тест явно обнуляет trial: общий helper теперь возвращает
идентификатор установки, и первый общий прогон выявил эту устаревшую фикстуру
(один CHECK). Production voice-путь не менялся.
Новая цель `test-sched-trial` входит в `make -C core check`.

## Граница результата и следующий шаг

Это предотвращение ложного **probe-confirmed**, а не доказательство
успеха браузера. Ранний буфер планировщика всё ещё хранит flowkey, не полный
binding/execution snapshot. Общая живая приёмка и перенос результата между
поколениями постоянной привязки требуют отдельной работы. HTTP уже имеет
свой более строгий путь. Для TLS/QUIC счётчики пакетов не заменяют критерий
соответствующего класса на живом потоке.

Fast-torrent/mailsuite не объявляются исправленными полем. Роутер, прогоны,
pcap и push не запускались. Общая goal остаётся активной; следующий шаг —
живая приёмка остаточных классов и воспроизведение входных различий HTTP
по предложенной владельцем pcap/pcapng-фикстуре.

## Следующее воспроизведение HTTP keep-alive

Во время общей проверки отдельный локальный Session-repro на текущем
производственном коде показал: полный Host и начало большого Cookie в
первом TCP-сегменте → первый запрос получает fake-badsum-whole; продолжение
Cookie и CRLFCRLF во втором сегменте → следующий самостоятельный GET /False/
на точной TCP-последовательности пропускается без плана. Причина в
`session.c`: при `!hr.end_known` сбрасывается `http_conn`, последующее
окончание заголовков уже не восстанавливает `http_next`.

Обе семьи дают exit 1 (два CHECK), лог
`/tmp/d2k-http-header-boundary-red.log`; путь к приватному исходнику/бинарнику
в `/tmp/d2k-http-header-boundary-repro-path.txt`. Это новое воспроизведение,
ещё не исправление и не включённый в check регресс. Следующим шагом перенести
его в штатный тест и восстановить учёт границы запроса по последовательному
потоку, без второго сборщика пакетов. Связь именно с полевым fast-torrent
требует pcap владельца; локальная фикстура не выдаётся за его захват.

Предварительная граница следующего исправления: один потоковый разбор
заголовков/Content-Length для Session и HTTP-наблюдателя. Нельзя восстанавливать
границу одним поиском CRLFCRLF: надо учитывать тело, дубли Content-Length,
Transfer-Encoding/Upgrade и последовательность TCP. Повтор уже обработанных
байтов не создаёт нового запроса; пропуск/неподтверждённое перекрытие не даёт
положительного свидетельства. Нужны положительные тесты разрезанного Cookie,
разрезанного Content-Length и тела, отрицательные — неоднозначного framing,
а также живой результат второго запроса и неизменное равенство его исполнения.
Сам разрезанный Host и конвейер внутри сегмента — отдельные входные случаи:
данный repro их не покрывает и не доказывает их исправления.

У наблюдателя есть ещё более ранняя граница: `http80.c` вызывает
`d2k_httpup_request_target`, а его `parse_request` в `core/httpup_logic.c`
требует целый GET/HEAD без тела в одном сегменте (`p + 2 == end`). При
разрезанном Cookie наблюдатель становится ST_DONE уже на первом сегменте.
Нельзя ослаблять безопасный разбор для HTTPS-перенаправления ради telemetry:
нужно отдельно сохранить доказанное имя/путь и завершить framing потоком,
связав раннее исполнение с тем же request seq. Это должно войти в регресс
вместе с повторным применением, иначе план заработает, а живая приёмка
останется слепой.

Отдельный приватный repro наблюдателя также воспроизведён:
`/tmp/d2k-http-observer-boundary-red.log`, exit 1, четыре CHECK (IPv4/IPv6:
не замечен полный первый ответ и не замечена вставка на втором запросе).
Тот же поток с заголовком целиком в одном сегменте — exit 0. Исходники и
контрольный вариант находятся по пути из
`/tmp/d2k-http-observer-boundary-repro-path.txt`. Это локальные синтетические
пакеты через production `d2k_http80_packet`, не полевой захват.
