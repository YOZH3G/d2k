# Отключаемая диагностика D2K

Реализация поверх `3636875`, ветка `work/diagnostics-1021`.

## Пользовательский контракт

В панели → «Диагностика» → «История памяти и подборов». По умолчанию сбор выключен. «Включить сбор» не перезапускает службы. «Скачать диагностику» выгружает локальный JSON. «Выключить и удалить историю» удаляет историю; контроллер освобождает кольца на ближайшем служебном такте. Перезагрузка роутера отключает сбор. Деинсталляция удаляет диагностическую историю и флаг включения, даже при сохранении каталога обходов. Перезапуск одного контроллера при включённом сборе начинает новую историю.

Никаких автоматических отправок, новых зондов, сбросов сессий, очистки каталога или изменения алгоритма поиска. Отчёт содержит имена и адреса целей, но не конфигурацию, ключи и содержимое пакетов; выгрузка — осознанное действие владельца.

## Пределы и нагрузка

- Единственный динамический буфер у контроллера: 64 завершения поиска + 120 снимков. На текущем arm64/macOS ABI 77 680 байт; compile-time предел 128 КиБ для всех ABI.
- При выключенном сборе этот буфер не выделен. Раз в секунду проверяется локальный флаг; дополнительных процессов нет.
- Снимок раз в минуту. Экспорт также раз в минуту: новые события могут появиться в скачиваемом файле с задержкой до минуты.
- Файл `/tmp/d2k-diagnostics/report.json` не более 256 КиБ. Атомарная запись через `report.new`: максимум два таких файла одновременно. Каталог 0700, файлы 0600. На стандартных роутерах `/tmp` находится в RAM, постоянный накопитель не используется.
- Панель читает не более 256 КиБ на выгрузку и освобождает память после ответа. Поэтому размер всей дополнительной истории, включая два файла и буфер ответа панели, ограничен, а не только число строк в интерфейсе.
- Сжатие не нужно: фиксированные компактные записи и ограничения проще и дешевле для CPU.
- `free` освобождает объекты; немедленное падение RSS не гарантируется поведением аллокатора. RSS — наблюдение, не доказательство утечки.

## Данные

`schema:1` относится только к диагностическому отчёту, не к JSON d2kfetch.

`events`: итог, локальный идентификатор поиска, протокол, семейство, цель и IP, форма, код подозрения, способ поиска, время и число зондов (если известно). TCP/QUIC/voice берутся из единого завершения планировщика; HTTP из терминальных веток httpsearch. Поле `reason_source` отличает контекст последнего классификатора от машинной причины завершения HTTP. `probe-confirmed` не означает загрузку страницы владельцем. Для HTTP число зондов и ожидание очереди пока неизвестны (`null`). Идентичность записи: выпуск + PID контроллера + протокол + id, а не один id.

`samples`: RSS/HWM/анонимная память/потоки ОС для d2kc, d2kd, d2ktg, d2kpanel; PID проверяется по comm. Общая и доступная RAM; привязки, планы, коробки, наблюдения, занятые задачи, активные замеры, очередь, число задач со снимками; записи и очередь HTTP. `system_conntrack` — счётчик системы, НЕ число потоков D2K. Точное число потоков датапата пока отсутствует в интерфейсе и явно `null`. Неизвестные значения не превращаются в нули.

Кольца хронологические; `events_overwritten` и `samples_overwritten` сообщают о вытеснении. UI показывает изменение RSS только между снимками одного PID. При пропуске времени или остановке контроллера дата последнего снимка остаётся видна; история не является непрерывной телеметрией гарантированного охвата.

## API

- GET `/api/diagnostics?status`: включён ли сбор.
- GET `/api/diagnostics?report`: текущий отчёт; 503/pending до первого снимка.
- GET `/api/diagnostics?download`: тот же JSON с Content-Disposition.
- POST `/api/diagnostics?enable` или `?disable`: существующая проверка `control_enabled` и same-origin; GET ничего не включает.
- Ответы no-store; слишком большой файл и симлинк не выгружаются.

## Проверка и границы

Регрессии проверяют пределы при миллионе записей, интервал, FIFO, неизвестные значения, JSON реального сериализатора, procfs-фикстуру, повторное включение/выключение в настоящем цикле контроллера, атомарную публикацию, HTTP-классификацию, callback без human logger, панель/API, отсутствие межсайтового управления, предел файла, удаление прерванного экспорта и браузерный default-off.

На роутере установлен диагностический кандидат: проверены выключенное начальное состояние, включение, минутные снимки памяти всех четырёх процессов, запись исходов поиска, скачивание, очистка при выключении и повторное включение. Длительное наблюдение реального роста памяти пока не выполнено. Измерение числа объектов не исправляет возможную утечку или рост самого каталога. Следующий этап — собрать историю во время реальной жалобы. Пользователь включает сбор в панели, воспроизводит проблему, скачивает отчёт и прикладывает файл к issue вместе с адресом цели, временем и описанием симптома. Перед публикацией отчёта следует учитывать, что он содержит домены и IP-адреса. Выключать сбор нужно после скачивания: выключение удаляет историю.
