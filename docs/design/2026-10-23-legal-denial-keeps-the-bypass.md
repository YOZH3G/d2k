# HTTP 451: приём снял блок рукопожатия, а мы не ставим ничего

Дата: 23.10.2026. Ревизия: d570a12 (worktree d2k-twoseg-1021, ветка
fix/twoseg-1021). Повод: issue #28 «x-minus.pro — подбор обхода прерывается
после HTTP 451» и замер того же вечера, который эту жалобу подтвердил.

## 1. Что измерено

Роутер на подписанном выпуске `d2k-20261022-1322-166840a`, прибор `d2kfetch`
с роутера. До замера:

```
x-minus.pro   приветствие: 1534 байт, TLS 1.3, через планы
              TLS: рукопожатия нет
              причина: нет TLS: чтение: Connection reset by peer
```

Три обращения завели поиск. Дословно, и это повторилось ДВАЖДЫ:

```
16:50:32 базовый вопрос донора: рукопожатие не проходит (0 из 3 — триггер
         целиком режется)
16:50:32 поставил план 1 из 4 (plan-9d543a55, порт зонда 59931)
16:50:33 HTTP 451: юридический отказ, не доказательство блокировки
         провайдера; перебор остановлен
16:50:33 итог: outcome=failed path=own-plan probe_units=4 elapsed_ms=547

16:52:58 поставил план 1 из 5 (plan-9d543a55, порт зонда 53991)
16:52:58 HTTP 451: ... перебор остановлен
16:52:58 итог: outcome=failed path=own-plan probe_units=4 elapsed_ms=4337
```

Адрес — 172.67.151.227, фронтенд Cloudflare. Ответ 451 получен ИЗ-ЗА
завершённого TLS к этому фронтенду, и наш же классификатор отнёс его к
`D2K_HTTP_LEGAL_DENIAL`, а не к `D2K_HTTP_BLOCKED` (`core/verify.c:1037`).
То есть это ответ сервиса, не подстановка провайдера.

## 2. Что из этого следует

Под планом `plan-9d543a55` запрос ДОШЁЛ до HTTP-края сервиса. Значит блок
рукопожатия этим планом снят — измеренный факт о плане.

А дальше (`core/sched.c`, ветка `D2K_VER_DENIED`) опыт выбрасывается: `ver_close`
снимает пробный план, `task_fail` закрывает задачу, в каталог не идёт ничего.
Пользователь получает не страницу сервиса с его отказом, а разорванное
соединение — то есть ХУЖЕ того, что мы уже умеем дать.

Разделение, которое здесь нужно и которого в коде нет:

| что доказано | чем |
| --- | --- |
| блок рукопожатия снят | ответ HTTP-края под планом |
| содержимое получено | НЕТ: сервис отказал по закону |

ТЗ требует различать вердикт, исполнение на проводе и успех приложения.
Сегодня код сливает «успех приложения не получен» с «план ничего не стоит».

## 3. Что сделано сейчас

Только бесспорная часть: 451 ставит остывание цели, как это делает соседняя
ветка антибот-ответа. Без него тот же сервис перемерялся заново каждые пару
минут (поиски 33 и 36 за 145 секунд, по 4 зонда и установке плана каждый) и
каждый раз получал тот же 451. Остывание называется в журнале своими словами:
«замер отложен после юридического отказа сервиса».

## 4. Что НЕ сделано и почему

Установка плана, снявшего блок рукопожатия, при отказе сервиса. Это изменение
правила подтверждения, а оно в проекте самое строгое: `verify_confirm` пишет
привязку, которую панель показывает как рабочую, и неверный шаг здесь молча
объявит цель решённой. Такое не делается в конце длинной смены по одному
замеру одной цели.

Что нужно, чтобы сделать это правильно:

1. Отдельное поле прикладного вердикта у привязки («сервис отказывает по
   закону»), чтобы панель не утверждала, что сайт работает.
2. Доказательство применения плана именно к потоку зонда (`ver_ok`) — как у
   обычного подтверждения, без скидок.
3. Условие пересмотра: сервис может перестать отказывать, значит привязка с
   таким вердиктом обязана перемеряться по сроку.
4. Решение владельца по сути: показывать пользователю страницу отказа сервиса
   вместо разорванного соединения — это улучшение или нежелательное
   «притворство, что сайт открылся»? Вопрос продуктовый, не технический.

## 5. Проверки

Регрессия на сделанную часть — в существующем блоке 451 `core/test_sched.c`:
после 451 новое подозрение по той же цели не начинает поиск, и журнал
называет причину. Прежние утверждения того блока сохранены без изменений:
привязка не пишется, перебор останавливается после первого ответа.
