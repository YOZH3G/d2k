# Полевой запуск D2K: TCP/TLS и QUIC-наблюдение — 27.09.2026

## Вывод

На живом Keenetic подтверждён TCP/TLS 1.3 путь D2K: пустой
временный каталог → поток клиента → автоматический поиск оригинального
инструмента → `disorder` → собственный verifier → сохранённая коробка →
три последовательные загрузки настоящей страницы YouTube клиентом за NAT.
В том же процессе и каталоге второй заблокированный hostname того же YouTube/
Google адреса получил готовый план узнанной коробки до нового замера.
Роутерный QUIC-путь в режиме наблюдения отдельно распознал реальные QUIC
Initial и здоровый HTTP/3 обмен. **Это не закрывает MVP:** контролируемая
деградация, reuse/persistence и TLS 1.2 закрыты последующими ретестами 27.09
(см. дополнение в конце); заблокированный QUIC-поиск/исполнение, независимая
вторая цель и штатный reboot/persistent-runtime остаются непроверенными.

Instagram не использовался. В начале и конце полевых опытов сервисов и
процессов z2k/D2K не было; постоянный `/opt` не менялся. Каждый прогон ставил
правила с уникальным комментарием и временные бинарники в `/tmp`; после каждого
удалены все правила-метки, очередь отвязана, процессы остановлены.

## Автоматический поиск и приложение: TCP/TLS 1.3

До активного опыта для закреплённого адреса `www.youtube.com` →
`142.251.155.4:443` были три подряд неуспешных TLS-запроса (HTTP 000, TLS
timeout, 0 байт); в то же время контрольный `www.google.com` отвечал HTTP 200,
`ssl_verify_result=0`. Instagram не затрагивался.

В `apply + LEARN`, с пустым каталогом в `/tmp`, правило было сужено только по
назначению `142.251.155.4:443`. Это намеренно не включало ограничение по LAN
источнику: собственные verifier-зонды исходят от роутера и должны попадать в
тот же datapath.

Последовательность в `control-20260927-110033.log`:

1. Автоматически обнаружен живой ClientHello `www.youtube.com`; после прихода
   полного снимка 325 байт поиск перезапущен с точными байтами клиента.
2. За 127 секунд и 18 зондов оригинальный C-поиск нашёл `disorder`; вердикт:
   «решает содержимое».
3. Кандидат `plan-0df173dd` поставлен первым; собственный verifier получил
   прикладной HTTP 200; каталог записал коробку `box-74131cd5`, TLS-план,
   name-binding уровня 3 и `verified_by: 1`.
4. Пока план был установлен, фактический клиент за NAT получил **три
   последовательных HTTP 200**. Последнее тело — 886 539 байт с
   `<title>YouTube</title>`.

Сохранённый каталог: одна коробка, один включённый TLS-план и одна подтверждённая
привязка к `www.youtube.com`; это собственное обучение, не импорт z2k-стратегии.

## Проверка reuse на второй цели в том же опыте

После 3/3 HTTP 200 на `www.youtube.com` передан второй hostname,
`youtube.com`, также закреплённый на `142.251.155.4`. До проверки готового
плана он дважды дал TLS timeout/HTTP 000. Контроллер сначала написал:

```text
по youtube.com проверяю 1 готовых планов узнанной коробки / совместимых моделей ДО нового замера
```

Затем применил тот же `plan-0df173dd`; собственный verifier получил HTTP 301.
Поскольку первый замер шёл по холодной заготовке, а позднее пришёл снимок
клиента, scheduler повторно проверил готовый план на точном снимке 321 байт;
verifier снова получил 301. Итоговый каталог содержит **одну** коробку,
**один** TLS-план и две level-3 name-привязки (`www.youtube.com` и
`youtube.com`); `successes=3` у плана, `verified_by=1` у обеих привязок.

Клиентский запрос к `youtube.com` получил 301 дважды, но curl не следовал
redirect, поэтому конечная страница после redirect не проверена. Это полевая
улика reuse-порядка на двух hostname одного сервиса/адреса, не утверждение о
совместимости с независимым доменом или другой DPI-коробкой. Полный каталог —
`docs/field/raw/catalog-20260927-110900.json`.

### Некорректная первая попытка и поправка

В прогоне `105303` я дополнительно сузил apply по `SRC=192.168.1.117`. Это
отсекло verifier-зонды самого роутера; поиск всё же нашёл `disorder`, но
проверка не увидела свой поток, и запись не сохранилась. Это ошибка области
полевого правила, а не опровержение стратегии. До перезапуска проверено, что
опыт полностью снят. Повтор `105721`/`110033` оставил только ограничение по
одному destination IP; собственный verifier попал в очередь и подтвердился.

## Дополнение 27.09 — деградация, сохранение и TLS 1.2

После первой версии отчёта проведены ещё три узких запуска на том же
Keenetic-0235. Во всех — только TCP/443 к `142.251.155.4`, правила с уникальным
жетоном, временные файлы в `/tmp`; ни z2k, ни Instagram не запускались.

### Контролируемый отказ старого плана → стратегия той же коробки

Для воспроизводимости seed-каталог содержал одну изученную коробку и
`plan-0df173dd`; в копии каталога `order reverse` было намеренно заменено на
`order forward`, чтобы гарантировать отказ. Это симуляция деградации известной
стратегии, не утверждение о самопроизвольном изменении DPI на линии.

- Клиент: первые 8 TLS-запросов к закреплённому YouTube адресу завершились
  таймаутом; следующие 7 прошли HTTP 200, TLS verify 0, тела 888–899 КБ.
- Контроллер сначала испытал готовый план распознанной коробки; тот не дошёл до
  TLS. Затем встроенный в исходный поиск poison-путь выдал
  `plan-aa40bdd1`; собственный verifier получил HTTP 200. При пришедшем полном
  клиентском ClientHello (325 байт) точный повтор также отверг старый план и
  подтвердил `plan-aa40bdd1`.
- Каталог после завершения: **1 коробка, 2 TLS-плана**; привязка
  `www.youtube.com` переключена на `plan-aa40bdd1`. Это подтверждает модель
  «коробка → несколько проверенных стратегий», а не клонирование коробки.

Этот опыт выявил дефект сохранения: первая версия после подтверждения оставила
на диске старый каталог, потому что d2kc считал dirty только по числу
привязок. Исправлено process-local `d2k_catalog.revision`: подтверждённые
изменения поднимают ревизию, контроллер сравнивает её при периодическом и
финальном сохранении. Следующий ретест сообщил `каталог сохранён (изменение 2)`;
Plan пережил остановку процесса и загрузился следующим запуском.

Сырые свидетельства деградации: `control-20260927-132411.log`,
`observe-20260927-132411.log`, `catalog-20260927-132411.json`. Неудачный прогон
до persistence-исправления: `control-20260927-131413.log` /
`catalog-20260927-131413.json`.

### Проверка после перезапуска контроллера

Следующий запуск загрузил сохранённый каталог (одна коробка, два плана) в
новый временный runtime. Пять последовательных запросов к тому же YouTube
endpoint сразу получили HTTP 200, TLS verify 0, тела около 891–897 КБ;
контроллер загрузил две привязки и не запускал поиск. Helper остановил
процессы, отвязал queue и удалил правила по жетону; `/opt` не менялся. Это
доказывает serialization → новый process → restore в тестовом режиме, но не
перезагрузку роутера и не штатный постоянный `/opt`-каталог.

Свидетельства: `control-20260927-132629.log`,
`observe-20260927-132629.log`, `catalog-20260927-132629.json`.

### TLS 1.2 на блокируемой цели

До запуска D2K прямой `curl --tlsv1.2 --tls-max 1.2`, закреплённый на тот же
адрес, получил TLS timeout / HTTP 000. Клиентская серия принудительно держала
TLS 1.2: первые 6 запросов timeout, следующие 6 получили HTTP 200. Scheduler
отклонил несовместимые опыты с причиной `нет TLS 1.2`; verifier затем ответил
HTTP 200 и сообщил, что сам говорил старой формой TLS 1.2. Привязка сохранена
с отдельной формой. Здесь переиспользован уже найденный Plan той же коробки,
а не доказывался cold search TLS 1.2 с пустым каталогом.

Свидетельства: `control-20260927-132725.log`,
`observe-20260927-132725.log`, `catalog-20260927-132725.json`.

## Оставшаяся приёмка MVP

- Нужна независимая вторая цель/служба, где сохранённый план приводит к
  полноценному клиентскому приложению (второй hostname того же Google/YouTube
  edge дал только redirect).
- Закончить blocked QUIC: живой вход → исходный QUIC `askArms` → точный wire
  apply → verifier и реальное приложение за NAT. Роутерный QUIC по-прежнему
  доказывает только здоровый observe; Docker ранее упирался в отсутствие
  conntrack-записи для verifier-потока.
- Проверить cold TLS 1.2 поиск с пустым каталогом, штатное постоянное
  хранилище/reboot роутера и отдельную полевую приёмку STUN/voice.

Каждый прогон завершён очисткой: на роутере нет процессов D2K/z2k, NFQUEUE
правил с жетонами и временных файлов `/tmp/d2k*`; Instagram не использовался.
