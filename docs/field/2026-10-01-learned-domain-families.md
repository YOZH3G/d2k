# Автоматические семейства: приёмка 01.10.2026

## Повторная приёмка после пользовательского сообщения

Исходники **`6419b2d`**, активная ветка `feat/telegram-tunnel`; согласованные
контроллер, датапат и панель уже установлены на ARM64-роутере. Ни DNS, ни
Telegram, ни сетевые правила не менялись. Развёртка принята внутри независимого
двухминутного окна отката, после восстановления обеих областей применения.

Первоначальная приёмка ниже подтверждала только TLS 1.3-семейство. Это было
недостаточно для завершения всей пользовательской задачи: отдельного QUIC-
семейства тогда ещё не было. Его обучение не требовало нового алгоритма:
общий штатный классификатор уже записывал собственные подтверждённые блокировки
QUIC. Три новые собственные проверки автоматически сформировали QUIC-группу.
Ручных доменных правил или превращения старых успехов в доказательства нет.

Обнаруженные и исправленные дефекты:

- Очередь показывала дату загрузки роутера: `started_ms=0` превращалось в
  стенное время boot. Теперь ожидающая задача показывает `queued_ms`.
- Пассивное наблюдение за подтверждённой привязкой и cooldown отображались
  как продолжающийся поиск. Они больше не входят в `live.searches`;
  подтверждённые планы остаются в каталоге.
- Повтор ClientHello после разобранного ServerHello или целой TLS data record
  ошибочно запускал раннюю диагностику. Сигнал теперь подавляется только по
  разобранному ответу, не по одному байту `0x17`. Оборванные/некорректные
  записи, ACK и поздние RST/FIN сохраняют свои диагностические пути.
- Очередь старого потока без обхода сохранялась после установки нового
  подходящего семейства. Она снимается без зонда и без точной записи только
  после коррелированного ACK. Порядок определяется последовательностью
  событий, поэтому enqueue и ACK в одном тике не спутываются.
- Такая отмена не может потерять последующую ошибку реально применённого
  плана. TCP-форма принадлежит исходному потоку, а не последнему снимку того
  же имени: очередь TLS 1.2 не отменяется установкой TLS 1.3. Если принадлежность
  неизвестна, отмены нет. Exact overrides и отрицательные исключения сохранены.

Ревью выявило три important и один minor; они исправлены одним проходом.
Новые пакетные и scheduler-регрессии воспроизвели дефекты до правки и прошли
после неё. Полные `core check`, `datapath check`, `detect check`, `panel test`
завершились успешно. Собраны все 27 обновляемых бинарников девяти архитектур;
остальные компоненты релиза не менялись.

### Реальные семьи и первые потоки

|---|---|---|---:|
| googlevideo.com | IPv4 / TLS 1.3 | plan-aa40bdd1 | 3 |
| googlevideo.com | IPv4 / QUIC | plan-389a3920 | 3 |

Новые `rr11` и `rr14` с окончанием `---sn-n8v7knel.googlevideo.com` получили

захват показал 11 fake Initial, побайтно совпадающих с payload семейного плана,
до пересылки настоящего клиентского Initial. Для этих трёх имён не возникло
поиска, exact binding или записи обучающего свидетельства.

Дополнительно получен **полный реальный видеопоток YouTube**, а не страница 404:
MP4/H.264, 192×144, 18,933 с, 284 читаемых кадра. Один CDN-хост без точной
привязки `rr2---sn-xguxaxjvh-8vbs.googlevideo.com` отдал HTTP 200 и **195278 байт**
как по TLS 1.3 (9,421 с), так и по HTTP/3 (10,862 с). SHA256 файлов совпал,

по имени по-прежнему отсутствуют. Signed URL, видеоданные и полные захваты
не включены в репозиторий. Это приёмка видеотранспорта, не интерактивного
браузера/телевизора: пользовательскую оценку старта роликов она не подменяет.

Один другой новый CDN-узел `rr18` не ответил на наследованный TCP-план, затем
не ответил и прямому измерению. Его точечная диагностика не скрыта и не выдана
за повторную проверку всех членов семейства. Причина недоступности этого узла
по одному таймауту не установлена; рабочие соседние узлы и группы сохранены.

После последнего обновления: Google TLS 1.3 — 200/0,377 с; Яндекс — 302/0,226 с;

## Проверенный пользовательский контракт

Три ранее не привязанных имени `rr3`, `rr4`, `rr6` с окончанием
`---sn-xguxaxjvh-bvwe.googlevideo.com` прошли штатный замер блокировки OPAQUE
и собственное подтверждение `plan-02dfb78d`. Каждый поиск занял 54 секунды.
Контроллер сам создал активное семейство `googlevideo.com`, TLS 1.3/IPv4,
с тремя свидетельствами, путём `/` и без ECH-origin. Ручных wildcard и
импорта прежних успехов для обучения не было.

Первый запрос нового `rr8---sn-xguxaxjvh-bvwe.googlevideo.com` завершился за
**0,174 с**. Захват пакетов подтвердил применение плана на первом ClientHello:
смещение TCP sequence на один байт назад, разделение 1400/1/115 байт.
Для этого имени не появились поиск, свидетельство обучения или точная привязка.

После перезапуска контроллера и датапата семейство восстановилось и получило
подтверждение установки. Ещё одно новое имя
`r8---sn-xguxaxjvh-bvwe.googlevideo.com` открылось за **0,155 с**, также без поиска
и точной привязки. Повтор — 0,094 с.

CDN-запросы возвращали ожидаемую HTTPS-страницу **404, 1561 байт**: это доказательство
доступного прикладного ответа и исполнения обхода, не воспроизведения видео.
Имена без видео-токена не могут доказать загрузку самого видеопотока.

## Реальное точечное отличие

`rr16---sn-n8v7znlk.googlevideo.com` из другой сети CDN не открылся с семейным
планом. Штатный адресный поиск проверил первый кандидат, затем подтвердил
`plan-aa40bdd1` и сохранил точную TLS 1.3/IPv4-привязку. После этого ответ получен
за 0,108 с. Сосед `r8` продолжил работать с семейным планом за 0,094 с.
Это положительный exact override, а не исключение DIRECT_CLEAR.

Таким образом, семейство — изученная гипотеза, не обещание одинакового поведения
всех CDN-узлов. Новые совместимые имена получают план сразу; реальная неудача
допускает собственный поиск, не разрушая рабочее семейство.

## Принятые решения и цена ограничений

- Последняя утверждённая спецификация важнее старой формулировки goal:
  немедленное наследование, а не проверка каждого нового имени. Цена ошибочной
  гипотезы — первый неудачный поток и последующее точечное исправление.
- Источник истины — свидетельства, не отображаемый `domain_groups`.
  Цена — пересборка семейства при запуске, зато метаданные не включают обход сами.
- Протокол управления обновлён согласованно до v6 (заменяет промежуточный v5):
  корреляция ACK и форма реального потока обязательны. Смешанная пара отвергается;
  цена — нельзя обновить только один runtime-компонент.
- PSL проверяет контроллер, датапат проверяет синтаксис и границы меток.
  Цена — доверие контроллеру; произвольный сторонний отправитель ctl не поддерживается.
- Чистый узел до объединения запрещает расширение; чистый узел внутри уже
  принятого семейства становится точным исключением. Цена — остальные узлы
  сохраняют гипотезу и требуют собственных исключений при реальном отличии.
- При заполнении 256 свидетельств отрицательные не вытесняются: сначала убираются
  неопределённые, затем только положительные; дальнейшее обучение замораживается.
  Исторические положительные голоса могут сохраняться вместе с отрицательными.
  Если новый отказ невозможно сохранить, семейства отключаются с сохранением
  точных привязок. Цена — потеря ускорения до отдельного решения о бюджете.
- Зашифрованные path/origin нельзя выбирать на пакетном уровне. Разные планы
  с одинаковым видимым ключом не активируют произвольное семейство;
  цена — в конфликтных случаях работают точные привязки.
- Proof-path длиннее 255 байт не сокращается и не участвует в обучении семейства.
  Цена — такие ресурсы остаются только точными привязками, без роста каждого слота.

Отложенный minor ревью: у имён-свидетельств внутри раскрываемых деталей семейства
нет прежней отдельной кнопки копирования. Управление службами сохранено.
Верхняя граница live RSS не измерялась; нет заявления о полной универсальности
семейств, Cloudflare-проверок или совместимости всех реальных моделей.
