## Шаг 1. Что именно делает механизм

### Наблюдения (источники событий обучения)

Все наблюдения пишет `group_record()` (`core/sched.c:4471`) в
`d2k_group_learn()` (`core/groups.c:108`). Ключ контекста `d2k_group_key`:
transport, IP-family, shape (TLS 1.2 / TLS 1.3 / ECH-TCP / QUIC), `probe_path`,
`ech_origin`. Адресные цели (`by_addr`) и имена без registrable domain по PSL
в обучение не попадают.

| Наблюдение | Кто порождает | Условие |
|---|---|---|
| `BLOCKED_CONFIRMED` (1) | `verify_confirm` (`sched.c:4564`) | прямой замер доказал блокировку (`PREFIX/WHOLE/OPAQUE` или объёмный обрыв, `group_block_proven`) **и** собственный verifier дошёл до приложения **и** датапат подтвердил APPLIED этого плана. Наследование семейного плана голосом не является. |
| `DIRECT_CLEAR` (2) | ветка CLEAR (`sched.c:5532`) | прямой замер дал `D2K_V_CLEAR` и `rx_direct_complete`. |
| `PLAN_FAILED` (4) | (а) восстановление семейства `family_fast` (`sched.c:5892`): verifier не дошёл до приложения, план тронул поток, уровень ≥ transport, без потерь событий; (б) постоянный отказ исполнения `D2K_REFUSE_TOO_LONG` на чужом клиентском потоке, чей план совпал с семейным (`sched.c:4925`) | (б) ещё и запускает `on_suspect` для имени. |
| `INCONCLUSIVE` (8) | **никто** | в `core/*.c` (кроме тестов) значение не порождается; ветка в `learn` мёртвая для рантайма. |
| `ADMITTED_EXCEPTION` (16) | `learn` | бит происхождения: `DIRECT_CLEAR` пришёл, когда имя уже покрывалось семейством. |

### Выбор суффикса и плана (`rebuild`, `votes`, `add_group`)

1. Для каждого `BLOCKED_CONFIRMED` перебираются суффиксы имени снизу вверх до
   registrable domain по локальному PSL (`d2k_domain_base`).
2. `votes()` считает различные имена-члены (не сам суффикс) того же ключа с
   битом `BLOCKED_CONFIRMED` и тем же `plan_id`. Любой член с `DIRECT_CLEAR` без
   `ADMITTED_EXCEPTION` обнуляет суффикс (вето расширения).
3. Порог — **3 голоса**. Из подходящих выбирается **самый широкий** суффикс
   (цикл перезаписывает `best` при каждом подъёме) — до registrable domain.
4. Для одного суффикса и ключа выборы плана: меньше `PLAN_FAILED` → больше
   голосов → новее → лексикографически меньший `plan_id`.
5. Бюджеты: 64 группы, 256 наблюдений. При переполнении — `frozen`;
   отрицательные не вытесняются; если отрицательное некуда записать —
   `disabled` и все группы гаснут. Ни `frozen`, ни `disabled` не сбрасываются.
6. `d2k_group_match()` для имени возвращает самую узкую группу, кроме
   имён с `DIRECT_CLEAR` или `PLAN_FAILED` по плану этой группы.

### Что ставится в датапат

`sync_areas()` (`sched.c:3272`) по одной идентифицированной команде с ACK
(протокол управления v6, `SET_SUFFIX/DEL_SUFFIX/SET_BYPASS/DEL_BYPASS`):

- **suffix-план** (kind 1) на каждую группу, если план есть в каталоге и нет
  конфликта двух планов на один видимый ключ;
- **BYPASS** (kind 2) на каждого члена с `DIRECT_CLEAR`, и на члена с
  `PLAN_FAILED`, если его план всё ещё избран и у имени нет точной level≥3
  привязки с **другим** планом;
- исключения ставятся раньше суффиксов.

В датапате (`datapath/plans.c:888-915`) порядок для потока с именем:
пробная запись порта → **BYPASS** (если есть — плана нет вообще) → точное имя
своей формы → grandfather → **suffix** → «имя знаем, форма другая». То есть
BYPASS проверяется раньше точной привязки, suffix — после неё. Таблицы: 64
suffix, 256 bypass.

### Что меняется в планировщике

- `installed_family_ready()` (`sched.c:3839`): если подтверждённая ACK группа
  совпадает с именем/формой/семейством и у имени нет своей точной привязки —
  подозрение без применённого плана (`planned=NO`) **не запускает поиск**
  (`sched.c:4240`), очередь снимается (`queued_family_ready`, `sched.c:5297`),
  результат замера отбрасывается (`sched.c:5422`).
- `family_recovery_start()` (`sched.c:3880`): подозрение на потоке, где план
  применён (`planned=YES`), сначала проверяет избранный семейный план, затем
  другие собственные подтверждённые планы братьев (точные level≥3 привязки с
  равными transport/family/shape/path/origin) — на exact trial port, verifier.
  Неудача всех → `family_fast=2` → обычный прямой замер и поиск. Задачи
  восстановления имеют приоритет в очереди (`sched.c:5300`).
- Новые голоса — только через обычный путь `verify_confirm`.
- Панель (`panel.js:672 coveredByFamily`) скрывает точные привязки,
  покрытые семейством, и показывает карточку семейства с числом
  свидетельств и исключениями.
- Не путать: `family_reuse` / `has_other_family_target_plan` в `sched.c`
  относятся к IP-семейству (IPv4/IPv6), не к семействам доменов.

### Таблица «состояние → провод → планировщик»

| Состояние для имени N и ключа K | Действие на проводе | Действие планировщика |
|---|---|---|
| < 3 голосов в любом суффиксе N | только точные привязки N | обычный путь: подозрение → прямой замер → готовые планы коробки → поиск |
| Семейство G покрывает N, своей точной привязки нет, исключений нет | первый поток N сразу получает план G (suffix) | подозрение `planned=NO` игнорируется, очередь снимается; голос не пишется |
| То же, поток N с планом G даёт подозрение `planned=YES` | план G продолжает стоять | `family_recovery_start`: план G и планы братьев на exact trial port; успех → точная привязка N; неуспех транспорта → `PLAN_FAILED`; всё исчерпано → прямой замер/поиск |
| N получил `PLAN_FAILED` по плану G (и нет точной привязки N с другим планом) | **BYPASS N**: ни suffix, ни точный план N (в т.ч. собственный подтверждённый с тем же plan_id) не применяются | N выпадает из `match`; обычный путь |
| N получил `PLAN_FAILED`, но у N есть точная level≥3 привязка с другим планом | BYPASS не ставится; точный план N | обычный путь для N |
| N — `DIRECT_CLEAR` до создания семейства | BYPASS N не нужен; суффиксы, содержащие N, **не создаются** (вето) | прямой путь, cooldown |
| N — `DIRECT_CLEAR` после создания (admitted) | BYPASS N | прямой путь; семейство живёт |
| N — `PLAN_FAILED`, затем `DIRECT_CLEAR` | BYPASS N **и** вето всего суффикса (дефект Task 2а) | семейство пропадает для всех |
| Все голосующие стали `PLAN_FAILED` или admitted `DIRECT_CLEAR` | suffix остаётся (дефект Task 3) | семейство продолжает покрывать новых членов |
| Журнал заполнен (`frozen`) / `disabled` | новые группы не учатся / все suffix сняты | навсегда до ручного вмешательства (дефект Task 3) |
| Перезапуск | — | группы пересобираются из наблюдений (`restore`); наблюдение `evidence=23` → `catalog_load` отказ → контроллер не стартует (дефект Task 2б) |

Дефекты 2а, 2б и оба дефекта `votes()` воспроизведены на `d080fef`
отдельной программой вне дерева (scratch, `core/groups.c` + `core/domain.c`):
`a evidence=23`, `restore=-1`; `new before=1`, `new after clear=0`;
«все провалились» и «все чистые» → `match` по-прежнему находит группу.

## Шаг 4. Альтернатива: проверка известных планов без семейства

Что уже есть без семейств (`sched.c:5553-5570`, `known_plans`):
подозрение → прямой замер (классификатор донора) → только при доказанной
блокировке — готовые планы коробок с тем же пассивным отпечатком,
упорядоченные по числу успехов → verifier каждого на exact trial port →
точная привязка. Это и есть §3.4/§9.5. Вариант «подсказка» дополнительно
ставит планы братьев по суффиксу первыми в эту очередь (как сейчас делает
`family_recovery_start`, но для **каждого** нового члена) и не ставит
suffix-план в датапат до проверки.

| Критерий | Семейство (сейчас) | Подсказка порядка | Без семейства |
|---|---|---|---|
| Первый поток нового члена | сразу с планом: 0,10–0,17 с TLS, ~1,1 с QUIC (поле) | без обхода; нет данных о времени | без обхода; нет данных |
| Время до рабочего соединения | то же | прямой замер (если сохраняется) + 1 verifier; нет данных | ≥ 54 с (поле, состав не записан) |
| Зонды на член | 0 | ≥ 1 verifier (+ прямой замер, если сохраняется) | прямой замер + verifier на каждый готовый план; нет данных |
| Записи каталога | 0 на член; 256 наблюдений общий бюджет | точная привязка на каждый член | точная привязка на каждый член |
| Применение к неизмеренному хосту | да (§3.2/§7/§9.1/§9.5 расходятся) | нет | нет |
| Ошибка обобщения | первый поток неудачника рвётся, затем восстановление (2/9 в поле) | отражается только в лишнем verifier | — |
| Протокол датапата (SET/DEL_SUFFIX/BYPASS, ACK областей) | нужен | не нужен | не нужен |
| Риск для чужих точных планов | BYPASS гасит точный план (Task 22) | нет | нет |
| Риск запуска | `restore` может уронить весь каталог (Task 2б) | нет, если наблюдения не нужны или нормализуются | нет |
| Деградация семейства | требует Task 3 | не нужна — каждое применение проверено | — |
| Панель | компактнее (скрытие хостов) | обычный список привязок (или группировка только отображения) | обычный список |

Где семейство объективно лучше: первое соединение нового CDN-узла, ещё ни
разу не виденного (SNI до этого не измерялся). У видео YouTube новые
`rr*---sn-*` узлы появляются постоянно; при любом проверяющем варианте каждый
такой узел стоит минимум одного проваленного пользовательского потока и
времени проверки. Это единственный измеренный выигрыш, и он большой.

Где хуже: всё остальное — нарушение порядка «проверка до применения»
по ТЗ, отсутствие сведений о том, сколько унаследовавших хостов были вообще
заблокированы, отдельный протокол областей, 8 исправляющих коммитов за сутки
и 7 открытых дефектов, из которых один (2б) способен остановить весь
контроллер после перезагрузки, а один (22) — выключить чужой подтверждённый
план.
