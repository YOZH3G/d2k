## HTTP: проверяем повторный запрос, связываем живой отказ с исполнением

Коммиты 246362e, f7384b9, 76e1f68, d772f2c, 583fe58:

- Зонд делает два последовательных GET на одном keep-alive соединении,
  полностью читает оба ответа существующим HTTP framing parser из verify.c.
  Для подтверждения нужны прежние два опыта, теперь каждый с двумя полными
  ответами без вставки. Один 200, оборванное тело или Connection: close
  keep-alive-приёмку не проходят.
- Связанный живой отказ передаёт наблюдавшийся GET-путь второму запросу:
  первый `/`, второй, например, `/False/`. Нет жёстко заданных сайтов/путей.
  Неподдержанный контекст (в том числе query, HEAD, неизвестный путь) отзывает
  старый успех, но не подменяется `/` ради повторного подтверждения.
  Cookies/Authorization не копируются; значения URL/query не журналируются.
- http80 разбирает последующие запросы на известной границе TCP и снова
  проверяет их первый ответ. Предыдущее исполнение не наследуется новым
  запросом. d2kd привязывает завершённое исполнение к tuple + request SEQ.
- HTTP_PORTAL в control v14 несёт execution, plan, trial, monotonic request
  start и безопасный путь. d2kc отзывает только свой текущий постоянный
  HTTP-план при связанном отказе. Чужой план/trial/family, неподтверждённое
  исполнение и запоздалый запрос предыдущего поколения его не удаляют.
  Новый portal больше не теряется в пятиминутном cooldown.
- S99d2k добавляет входящие HTTP:80 PSH после первоначального окна пакетов
  в iptables/nft: без этого поздние ответы keep-alive могли не попасть к
  наблюдателю. IPv4/IPv6 и симметричное удаление проверены stub-тестами.

Это **отрицательная живая приёмка**: наблюдавшийся portal опровергает успех
конкретного исполнения. Она ещё не является общим положительным критерием
каждого класса и не доказывает, какой следующий HTTP-кандидат сработает в поле.
Изменены вопросы приёмки и отзыв знания, не байты существующих кандидатов.
Вопросы разреза Host, checksum-приманки и их произведения остаются измерением.

Ограничения: GET/HEAD должен быть разобран целиком на известной границе;
Location — виден в первом пакете ответа; действует проверка раннего ответа
по RTT. Deferred completion пока не получает такую HTTP execution-привязку.
Путь зонда не воспроизводит cookies, авторизацию, первый browser URL или
произвольные тела. Пайплайнинг и произвольное разбиение HTTP требуют отдельной
проверки. Отсутствие события при неполной видимости не означает live PASS.

## RX: HTTP0 больше не скрывает незавершённую TLS-запись

7d3d846 сохраняет первую частичную HTTP-выдачу, даже если повтор недоступен.
CLEAR после такого незавершённого измерения становится INCONCLUSIVE;
это не доказательство блокировки и не основание объявить прямой успех.

e2d679d добавляет в собственные TLS1.2/1.3 receive loops:

- `rx_tls_wire_bytes`: реально полученные recv байты после успешного
  рукопожатия, включая TLS headers/ciphertext/tag/post-handshake records;
- `rx_tls_record_missing`: недостающий остаток объявленной TLS-записи;
- `negotiated_tls`: фактически согласованная версия.

Это не IP-байты, не TCP retransmissions и не расшифрованное HTTP-тело.
Полностью принятая запись с плохим tag имеет missing=0; неполный TLS header
не сообщает известную длину остатка. Handshake исключён снимком счётчика.
TLS1.3→1.2 fallback складывает непересекающиеся recv-счётчики; переданный
в памяти ServerHello второй раз не учитывается.

Коммит 2d26ee7: отдельная сигнатура `rx-volume-wire` допускается только при двух HTTP0 после
успешного TLS с совпавшим именем, незавершённой записью, RX не менее прежнего
порога 12 КиБ и близкими объёмами (прежний допуск 4 КиБ). Контроль той же
цели/IP/path/hello и согласованной версии должен дать полный 2xx gzip,
причём его TLS wire объём меньше обоих обрывов. Локальный лимит, плохой tag,
неизвестная версия, смешанная body/wire пара и неоконченный контроль не
принимаются. Нового вывода «таймаут = DPI» нет.

Ciphertext-объём хранится отдельным видом приметы, не сравнивается с
`rx-volume` HTTP-body. Подтверждённая пара направляется в существующий RX
поиск с тем же измеренным пакетным бюджетом и общим исполнителем Plan.
Один частичный результат сохраняет неопределённость, а не запускает обход.
Смешанная пара старого mailsuite не доказывает новую сигнатуру задним числом.

## Общая приёмка классов: что осталось

| Путь | Имеющееся доказательство | Остаток живой приёмки |
|---|---|---|
| HTTP portal | COMPLETE конкретного запроса + связанный portal отзывает план | положительный результат каждого полного ответа и неполная видимость |
| TCP C / SNI | свой Plan runtime + собственный TLS/application verifier | class-proof на живом применённом потоке, отдельно от приложения |
| RX volume | парная body либо wire сигнатура + verifier бюджета | успех клиента сверх измеренного порога; не общий внешний TLS type23 |
| QUIC | свой протокольный handshake/H3/budget, единый UDP executor | encrypted live datagram не доказывает H3/второй stream |
| STUN / voice | протокольный STUN/voice proof соответствующего потока | общий контекст execution/generation и дальнейшая живая приёмка |

В catalog `verified_by` уже отделяет собственный зонд от клиента.
`on_exchange` не повышает TLS type23 до приложения, но освобождает WATCHING;
это ещё не общий механизм class-specific live acceptance. Текущая работа
не объявляет этот долг закрытым. #14, #4, #12 сохраняются в общей goal;
QUIC не блокирует открытие сайтов, доступных по TCP.

## Следующий локальный шаг общей goal

Сохранять общий контекст живого свидетельства от Session до core. Сейчас
`plan_handed_off` / `d2k_session_sent` знают execution и завершение raw sends
и original verdict, но journal→ctlsrv→link теряет execution/generation;
EXCHANGE сообщает протокольные признаки без полного контекста исполнения.
Нужны epoch d2kd, поколение потока и установленной привязки (в том числе
same-hash reinstall), execution/plan/trial и key type/protocol/shape.
Контекст снимается при выборе плана, а не восстанавливается по новой таблице.

Отдельный ограниченный журнал вне lifetime scheduler task должен хранить
три независимых факта: исполнение, критерий класса и результат приложения.
Для C ServerHello может снять конкретный симптом обрыва приветствия, но не
доказывает HTTP. Для RX прогресс сверх измеренного порога — свидетельство
прохождения этого порога, не полнота зашифрованной страницы. STUN transaction
или discovery SSRC не означают успешный голос. TLS/QUIC application остаётся
UNKNOWN без доступного протокольного доказательства.

Первый тестовый набор: переустановка того же hash, reuse пятёрки потока,
перезапуск d2kd, ответ до DONE, deferred send/original verdict, старый отказ,
дубли/потеря событий, собственный зонд вместо клиента. Неполная или чужая
идентичность не должна повышать live outcome либо отзывать новое решение.
Это следующий этап реализации, не уже реализованная общая приёмка.

## Продолжение: неизменяемая привязка исполнения

Коммит 8608f67 добавляет локальную идентичность установки Plan. Каждая
успешная установка name/addr/suffix/exact-flow получает новое поколение,
включая повторную установку того же hash. Session копирует поколение, тип
ключа, семейство, форму и временность при передаче плана на исполнение.
DONE/UNSENT/DAMAGED хранят этот снимок вместе с execution ID; поздняя
отправка не заимствует привязку из уже заменённой таблицы. Это метаданные
исполнения, не изменение TLV, hash или пакетов.

Регрессы: пустой getter давал 40 CHECK-провалов (exit1), отсутствие снимка
Session — два (exit1); после реализации оба проходят. При ревью найден
ещё один переход: новый SYN на прежнем 5-tuple сохранял ожидающие отправки,
но обнулял их binding. Новый Session-регресс без следующего ClientHello
даёт один CHECK-провал и exit1 на 8608f67; сохранение execution_binding в
d2k_track_new_connection делает его зелёным. Логи:
`/tmp/d2k-binding-red.log`, `/tmp/d2k-binding-session-red.log`,
`/tmp/d2k-binding-syn-red-run.log`, `/tmp/d2k-binding-syn-green.log`.

Это только основание для общей живой приёмки. Control остаётся v14:
общие APPLIED/EXCHANGE ещё не доставляют новый контекст в контроллер.
Нужны идентичность запуска службы и поколения соединения, связанное
наблюдение результата класса и раздельный учёт исполнения/критерия/
приложения. В частности, сохранение старой очереди через SYN не разрешает
приписать ответы нового соединения старому исполнению. Текущие тесты
проверяют сохранность отчёта отправки, а не такую положительную приёмку.
Это следующий локальный пункт; поле и 19/19 остаются неподтверждёнными.
