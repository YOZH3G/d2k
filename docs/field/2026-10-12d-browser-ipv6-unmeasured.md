# Поле 12.10.2026d: браузер идёт по IPv6, а подтверждён план по IPv4

Первый прогон с ЖИВЫМ критерием: настоящий Chrome ведётся по протоколу
отладки (не headless), и `response.protocol` даёт по каждому запросу `h3`,
`h2` или `http/1.1`, а статус документа — открылась страница или нет. До сих
пор колонка `live` во всех строках всех прогонов стояла `unknown`.

Роутер: ревизия b801eca (сегодняшние правки после неё НЕ развёрнуты), d2kc
жив, каталог 105 КБ, «поставлено планов по подтверждённым привязкам: 125».

## Решающий опыт

| Имя | Обычный Chrome (предпочитает IPv6) | Chrome с `--host-resolver-rules=MAP … <IPv4>` |
|---|---|---|
| nnmclub.to | `ERR_TIMED_OUT` ×3 заходов (ожидание 35 с) | **h2/200** оба захода |
| rutracker.org | `ERR_TIMED_OUT`, затем `ERR_ABORTED` | **h2/200**, 4 и 12 запросов |

Два имени из двух. Это не артефакт скрипта: ожидание поднималось до 35 с,
между заходами пауза 3 с, профиль чистый, и с выключенным QUIC
(`--disable-quic`) результат тот же — значит дело не в предпочтении h3.

## Что об этом говорит сам D2K

```
12:48:58 по nnmclub.to подозрение было ложным: план plan-680fbe00, под которым
         шёл поток, переподтверждён с проверкой бюджета — поиск окончен
12:52:41 по nnmclub.to подозрение при подтверждённом плане — наблюдение прекращаю
```

Дальше — **ни одной строки про nnmclub после 13:00**, пока я открывал его
браузером трижды и он трижды не открылся. Поиск прогона, который его
подтвердил, в журнале помечен `family=4`.

## Диагноз, и он точнее, чем «IPv6 не поддержан»

IPv6 поддержан: на роутере по 12 правил NFQUEUE в `iptables-save` и в
`ip6tables-save`, а в каталоге **45 привязок `family:6`** против 100
`family:4`. То есть машина целиком работает, и это НЕ отсутствующая
вертикаль.

Дыра — **по имени и по семейству адресов одновременно**:

1. По IPv4 имя измерено, план подтверждён собственным зондом и переподтверждён
   с проверкой бюджета;
2. по IPv6 то же имя не измерено НИКОГДА — и, что хуже, по нему не возникает
   даже ПОДОЗРЕНИЯ: восемь минут мёртвых потоков браузера не оставили в
   журнале ни строки;
3. браузер при наличии AAAA предпочитает IPv6, поэтому пользователь получает
   мёртвый сайт, а каталог в это время сообщает «подтверждён».

AAAA есть у 11 имён из 15 проверенных: nnmclub.to, rutracker.org, fost.club,
lostfilm.tv, katzauction.com, kinozal.me, adguard.com, enimerosi.com,
romfea.gr, rua.gr, spzh.eu. Нет у flibusta.is, fast-torrent.ru, mailsuite.com
(rutracker.cc не разрешается вовсе). И это объясняет, почему в браузере
открылись именно те, у кого AAAA нет: flibusta и mailsuite вынуждены идти по
IPv4, где план есть.

Попутно объясняется и расхождение с curl: `curl -I` по nnmclub отдавал
**HTTP/2 200** — он шёл по IPv4 (188.114.96.11). Один и тот же сайт в одну и
ту же минуту: по IPv4 работает, по IPv6 мёртв.

## Чего этот замер НЕ объясняет

**Почему по IPv6 нет подозрения.** Поток браузера умирает молча, без RST, и
датапат не сообщает о нём ничего. Это тот же случай «цель исчезла без улик»,
который разбор 12.10 нашёл для QUIC (задача 36), только здесь он на TCP и по
IPv6. Из наблюдения не следует, что именно мешает: правила его не ловят,
или ловят, но молчание не опознаётся сигнатурой, или задача по цели была
занята/на остывании. Это и надо выяснить первым.

## Остальной живой критерий того же прогона

| Цель | Документ | Протокол |
|---|---|---|
| www.google.com | 200 | **h3** (28 из 31 запроса) |
| enimerosi.com | 200 | **h3** со второго захода |
| romfea.gr | 403 | **h3** со второго захода |
| mailsuite.com | 200 со второго захода | h2 (11), http/1.1 (8), h3 (4) |
| kinozal.me | 200 со второго захода | h2 |
| adguard.com, flibusta.is | 200 | h2 |
| rua.gr, spzh.eu | первый ответ есть, затем `ERR_HTTP2_PING_FAILED` | h2 |
| nnmclub.to, rutracker.org, rutracker.cc, fost.club, fast-torrent.ru, lostfilm.tv, katzauction.com | не открылись | — |

Два вывода из таблицы, кроме главного:

- **QUIC действительно несёт трафик браузера** — enimerosi и romfea отдали
  документ по `h3`. Измеренный план `plan-e0d1dad8` подтверждён не зондом, а
  приложением; раньше такого свидетельства у проекта не было ни одного.
- **Новый класс, которого в таблицах не было**: rua.gr и spzh.eu отдают первый
  ответ, а затем соединение умирает с `ERR_HTTP2_PING_FAILED` — остановка
  потока на TCP/h2. Направление такой остановки правка 12.10 научила называть
  для QUIC; для TCP оно по-прежнему не названо.

## Инструмент

`scratchpad/h3probe.mjs` — Chrome с `--remote-debugging-port`, события
`Network.responseReceived`, по два захода на имя (alt-svc Chrome узнаёт только
из ответа, поэтому h3 выбирается со второго). Профиль временный, чтобы не
трогать профиль владельца. Не headless: §«поле и UI — только браузерами».
