# `core/test_compose` зависает на стенде — воспроизведение, не правка

Дата: 23.10.2026. Ревизия: 32e84f2 (worktree d2k-twoseg-1021, ветка
fix/twoseg-1021). Найдено по ходу работы над issue #7; к ней не относится.

## Что происходит

`make -C core check` не доходит до конца: `./test_compose` висит бессрочно и
не печатает ни строки. Сторож на 150 с снимает его по SIGKILL (RC=137).

Стек в момент зависания (`sample`):

```
d2k_props_ask  (in test_compose)
  d2k_props_ask_traced  (in test_compose)
    d2k_link_next  (in test_compose)
      poll  (in libsystem_kernel.dylib)
```

Сопутствующее состояние процесса: стенд `ctlprobe` жив дочерним процессом на
`/tmp/d2k-core-compose-<pid>.sock`, у теста слушающие сокеты на `[::1]` и
`127.0.0.1`, и одно соединение к своему же стенду в `CLOSE_WAIT` — то есть
сторона стенда закрылась, а тест продолжает ждать события из звена.

## Что проверено

| проверка | результат |
| --- | --- |
| повтор в рабочем дереве | висит там же |
| полная пересборка `make -C core clean` | висит там же |
| ЧИСТОЕ дерево `git archive 32e84f2` в новый каталог | **висит там же** |
| повтор в чистом дереве под сторожем | висит, RC=137, ноль вывода |
| то же дерево БЕЗ собранного `ctlprobe` | не висит: «стенд не поднялся», 21 провал |

Значит зависание не внесено правками дня и воспроизводится на чистом HEAD.
Оно требует поднятого стенда: без стенда тест честно падает.

## Чего это НЕ доказывает

Что причина в коде ядра, а не в окружении этой машины. Тот же `make -C core
check` проходил на ней сегодня раньше, и что изменилось между прогонами, пока
не установлено. Поэтому это запись воспроизведения, а не диагноз.

## Что не затронуто

Правка дня (снятие недостижимых вопросов) живёт только в `detect`. Из `core`
заголовок `d2k_detect.h` видит ровно один файл — `core/test_probe_plan.c`, и он
зелёный: `probe-plan: 12 inputs, 85 catalog hypotheses, 12 questions, 31
skipped, 0 mismatches`. `test_compose` не линкует `detect/props.c` вовсе
(`core/Makefile:542`), а `d2k_props` — свой тип `core/include/d2k_compose.h`,
не `d2k_dprops`. Общей памяти между правкой и зависанием нет.

## Следующий шаг

Отдельная работа: снять `CLOSE_WAIT` в разборе (кто закрыл стенд и почему
`d2k_link_next` не получает события закрытия), затем падающий тест на таймаут
ожидания вместо бессрочного `poll` — бессрочное ожидание в тесте само по себе
дефект: оно превращает отказ стенда в зависание прогона.
