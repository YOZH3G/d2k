RUTRACKER: ПОДТВЕРЖДЁННЫЙ РУЧНОЙ ОБХОД — ОПОРНАЯ ЗАПИСЬ
========================================================

Результат зафиксирован пользователем в этой беседе (скриншот отчёта Codex).
Это обязательный эталон для автоматического D2K-поиска; не терять и не
подменять похожим рецептом из комментария в коде.

Подтверждённая последовательность
---------------------------------
1. Точную стратегию из обсуждения Zapret2 #186 проверили отдельно с `nodrop`:
   RuTracker сбросил соединение. Сама по себе эта комбинация не рабочая.
2. Затем применили fake TLS с SNI `hcaptcha.com`, разделили настоящий
   ClientHello и убрали `nodrop`. Критическая поправка: исходный настоящий
   ClientHello нельзя выпускать целиком.
3. Большая HTTPS-страница загрузилась полностью: HTTP 200, 96 460 байт за
   0,58 с; повтор — HTTP 200, 96 460 байт за 0,57 с. Захват подтвердил, что
   fake-пакеты ушли первыми, полный настоящий ClientHello не ушёл, сброса не
   было.
4. Контроль без стратегии: сжатая страница открылась, незжатая загрузка
   остановилась примерно после 23,9 КБ — это согласуется с блокировкой по
   объёму.
5. HTTP-путь не эквивалентен описанию из обсуждения: `http://rutracker.org`
   перенаправляет на портал провайдера `lawfilter.ertelecom.ru`, а не на HTTPS.
   Поэтому гипотеза HTTP→HTTPS redirect не объясняет HTTPS-затык RuTracker.

Ссылка на исходную стратегию, проверенную отдельно:
https://github.com/bol-van/zapret2/discussions/186

Что пока НЕ известно из доступной записи
----------------------------------------
Скриншот подтверждает состав приёма и wire-результат, но не показывает точные
позиции/число разрезов ClientHello, параметры fake TLS (кроме SNI) и
последовательность всех правил профиля. Не выдумывать эти параметры. Для
автоматизации нужно получить/сопоставить полный транскрипт предыдущей проверки
или заново снять её конфигурацию и pcap; затем воспроизвести тот же план в
D2K и сверить побайтно существенные wire-параметры.

Важно: прежнее общее плечо с 8 повторами и `rnd,dupsid` удалено из обычного
fallback-перебора. Вместо него после подтверждённого RX-volume профиля есть
отдельные кандидаты `hcaptcha.com` + один stale-TS fake + разрез исходного
ClientHello в позициях `+2,+1,+3,+4,+5`. Это целевой поисковый ряд, а не
восстановленный точный эталон: неизвестные параметры остаются гипотезами до
проверки плана на роутере и wire capture.

Состояние переноса на 30.09.2026
--------------------------------
В `core/volume.c` измеритель делает два GET с `Accept-Encoding: identity` и
контрольный GET с gzip, отдельно от TX-лестницы. Для RX-диагноза требуется:

* оба identity-ответа — 2xx, неполные, с однозначным одинаковым HTTP framing;
* обрывы — не меньше 12 КБ и отличаются не более чем на заданный slack;
* framing не противоречив (например, нельзя принимать одновременно
  Content-Length и Transfer-Encoding), gzip-ответ действительно gzip,
  непустой и дошёл до конца.

Замеры идут через SO_MARK, не через установленный кандидат. Переход на
`rx-volume` переобучает примету коробки; сохранённые планы этой коробки
проверяются раньше нового кандидата, а уже проверенный текст не дублируется.
Verifier следует только same-origin HTTPS redirect (включая переход
`/` → `/forum/index.php`) на той же TLS-сессии и засчитывает только целое
тело. Это важно для результата HTTPS-проверки, но само по себе НЕ решает
обычный HTTP-вход.

`core/compose.c` теперь содержит отдельную короткую лестницу fake-SNI
кандидатов `hcaptcha.com` с разрезанием исходного ClientHello на соседних
позициях `+2`, `+1`, `+3`, `+4`, `+5`. Она вызывается только после
подтверждённого парного RX-volume-профиля и сохранённых планов совпавшей
коробки. Это гипотезы, построенные из подтверждённых ингредиентов; точные
mutation-параметры и успешная позиция ещё не сопоставлены с прежним capture. В обсуждении
#186 предложен пример с `tcp_ts=-1000`, `pos=2`, `repeats=1`, `nodrop`; по
записи владельца именно вариант с `nodrop` RuTracker сбрасывал, поэтому
переносить его буквально нельзя. Успешный ручной отчёт отдельно говорит,
что `nodrop` убран и исходный ClientHello нельзя выпускать целиком. [Ссылка на
обсуждение](https://github.com/bol-van/zapret2/discussions/186).

Чтобы этот профиль вообще мог инициировать замер по живому трафику, поздние
входящий серверный и исходящий клиентский TCP RST теперь отдельными
низкочастотными правилами доходят до datapath после окна первых пакетов. Они
порождают особый сигнал только если для потока уже видели TLS app-data. Сам
сигнал НЕ считается блокировкой: scheduler запускает
только парное измерение RX-объёма и разрешает подбор лишь при двух похожих
неполных identity-ответах плюс полном gzip-контроле. Обычный поздний RST,
который не подтверждается этим измерением, заканчивается без кандидатов.
Изменение перенесено на активную feat/telegram-tunnel вместе с IPv6,
Telegram и защитой DNS. Автоматические проверки направлений, обхода loopback,
сериализации firewall и HTTP+IPv6 прошли в изолированном контейнере.

HTTP-вход получил общий механизм реализации, но полевая приёмка ещё открыта.
В `core/httpup.c` GET/HEAD проходит через прозрачный IPv4 relay. Если реальный
ответ — междоменный HTTP 30x на hostname с явным portal-маркером (`lawfilter`,
`blocked`, `blockpage`, `censorship`, `access-denied` и т. п.), relay возвращает
временный переход на HTTPS исходного host/path. Так браузер сам создаёт TLS
поток и запускает штатное распознавание D2K. Обычный cross-host login redirect
без такого маркера проходит неизменённым; адреса роутера и непосредственно
подключённые сети исключены на уровне NAT. Остальные private destinations
намеренно не исключаются целым RFC1918-блоком: ISP DNS sinkhole сам может быть
приватным адресом. Здесь нет правила по `rutracker.org` и нет общего
принудительного HTTP→HTTPS для всех доменов. Новый helper, NAT-маршрут,
conntrack-метка его upstream и чистая установка/удаление добавлены в код,
собраны и развернуты на ARM64-роутере из активной ветки.

Критерии автоматического переноса
---------------------------------
- Проверить отрицательные границы чистого RX matcher, portal-редирект
  распознавателя и firewall/mangle исключения, затем остальные автоматические
  регрессии; только после завершения реализации перейти к живому роутеру.
- На живом пользовательском трафике подтвердить, что автоматический поиск
  распознаёт RX-объёмный профиль, сначала проверяет планы совпавшей коробки,
  затем пробует fake TLS/SNI + разрезание, без `nodrop` и без выпуска полного
  исходного ClientHello.
- При успехе сохранить фактический plan text/ID, wire capture, статус, полные
  байты и две независимые пользовательские проверки HTTPS; перезапустить
  D2K/повторить трафик и убедиться, что выбранный план не потерян.
- Отдельно подтвердить обычный пользовательский вход (ввести голый домен и
  перейти с HTTP, не подставляя вручную `https://`): исходный portal redirect
  должен быть преобразован в HTTPS исходного домена, TLS-поиск должен пройти,
  а 200/полное тело должно попасть в браузер. Повторить для обычного
  cross-host login redirect без portal-маркера: он обязан остаться прежним.
- Проверить перенос признака `rx-volume` между разными именами при совпадении
  коробки, а также регрессии TLS 1.2, TLS 1.3 и QUIC.
